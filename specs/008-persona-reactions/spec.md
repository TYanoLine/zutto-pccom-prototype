# Spec: ペルソナ特性にもとづくレス・反応の選択（人間の投稿への反応を含む）

**Spec ID**: 008-persona-reactions  
**Status**: Draft  
**Depends on**: `world.ThreadReplyCount`（スレッド単位のレス数）が `main` にあること。タスク T000 で確認する

## 背景

現状、レスの「数」はスレッド単位の確率分布で決まる（`world.ThreadReplyCount`）が、レスの「担い手」と「相手」は
ペルソナの特性をほとんど見ていない。実コードで確認した現状:

1. **誰が書くか**は、活動度（`activity_pattern`、`lurker_tendency`）と時間帯の揺らぎの順位だけで決まる
   （`bbsengine.actorRoster`）。返信向きの性格（`ReplyTendency`）、興味、議論好き（`Argumentativeness`）、
   新人への対応（`NewcomerOpenness`）は、選定に使われていない。
2. **どの記事に返すか**は、直近のルート記事からの一様ランダム（`planSlots`）。興味や関係は見ていない。
3. **人間の投稿**は `Store.AddPost` で保存されるだけで、反応を計画する処理がない。NPC のレスの候補に偶然入ることはあるが、
   特別扱いも、無視される判断も、どちらも設計されていない。人間のアペ（追記）は返信先の候補にもならない。
4. ペルソナの個性は、返信者が決まったあとの**文章生成**にだけ使われている（`personaSummary` ほか）。
5. `docs/WORLD_SIMULATION.md` には外部の助言モデル（Jev）による傾向の助言が書かれているが、記事生成のエンジンからは
   呼ばれていない（`worldengine.BehaviorAdvisor` の呼び出し元がない）。

`AGENTS.md` と `docs/WORLD_SIMULATION.md` は、行動の決定を World が行い、LLM は言語化だけを担うこと、
無反応・遅延・NPC どうしの会話の継続を正常とすることを求めている。この spec は、その決定を**統計・確率モデルだけで**
（LLM を呼ばずに）行う仕組みを定める。

## 設計の原則

- **決めるのは World。** 誰が反応するか、しないか、いつか、は決定論的な確率サンプリングで決める。LLM は決まった行動を言語化するだけ。
- **LLM は決定に使わない。** 助言モデル（Jev など）は、この経路では使わない。決定の速度とコストは、数値計算だけで決まる。
- **人間も NPC も同じ入口。** 人間の投稿を特別扱いしない（必ず反応が付くことも、必ず無視されることもない）。
  `AGENTS.md` の「人間は世界の一員であり、主人公ではない」に従う。
- **数式の係数は、架空の調整値。** 歴史統計ではない。コードとドキュメントに、そう明記する。
- **確定した事実は変えない。** 反応の計画は保存し、一度実体化した投稿は書き換えない。

## ユーザーストーリー

### US1: 人間の投稿に、ふさわしいペルソナが、自然な遅れで反応する（Priority: P1）

利用者として、板に投稿やアペをしたあとで、その内容や板に関心がある、しかるべき住民が、時間をおいて返信してほしい。
返信がまったく付かないことも、ときどきあってよい。

**Independent Test**: 人間の投稿を 1 件保存すると、反応の計画（担い手、遅延、順序）が決定論的に作られる。
計画された時刻を過ぎたあとに板を観測すると、その返信が記事として現れ、返信先は人間の投稿になっている。
同じ入力から、何度計画しても同じ結果になる。

### US2: NPC どうしのレスも、同じ基準で選ばれる（Priority: P1）

運用者として、NPC のスレッドのレスも、一様ランダムではなく、ペルソナの特性で選ばれてほしい。

**Independent Test**: 固定シードで十分な回数のスレッドを計画したとき、ゲームに興味が強い住民は、ゲーム関連の記事に、
そうでない住民より有意に多く返信する。ROM 専（`lurker`、`dormant`）は、ほとんど返信しない。

### US3: 返信の担い手の選択に LLM を使わない（Priority: P1）

運用者として、反応の決定にかかる時間とコストが、LLM の呼び出しに依存しないでほしい。

**Independent Test**: 反応の計画と、返信ヘッダの実体化を行っても、LLM プロバイダの呼び出し回数が増えない（テスト用の偽プロバイダで 0 回）。
LLM が使われるのは、読まれた返信の本文を生成するときだけ。

### US4: 返信の振る舞いが、性格と状況で変わる（Priority: P2）

利用者として、議論好きの住民は議論のあとに続けて返信しやすく、面倒見のよい住民は新人の投稿に返信しやすく、
スレッドを立てた人は返信に戻ってきやすい、といった傾向があってほしい。同じ人が同じスレッドで延々と返信し続けることはない。

**Independent Test**: 統計テストで、`Argumentativeness` が高い住民は、2 件目以降の返信に選ばれやすいこと、
`NewcomerOpenness` が高い住民は、新人の投稿に選ばれやすいこと、スレ主の戻り返信の確率が、非スレ主の返信確率より高いこと、
同じ人が同じスレッドに連続で返信しないことを確認する。

## 要件

- **FR-001（反応の計画）**:
  World は、記事（人間・NPC を問わない）が保存された時点で、その記事に対する**反応の計画**を作る。計画は、
  返信の本数、各返信の担い手（ペルソナ）、各返信の予定時刻、の組。純関数的（同じ入力から同じ結果）に作る。
- **FR-002（本数）**:
  本数は、板の `reply_rate` と記事の通し番号から、既存の `world.ThreadReplyCount` で決める。人間の投稿にも同じ法則を適用する
  （板ごとに、人間の投稿だけ別の倍率を持たせない）。本数 0 は正常な結果として扱い、返信は作らない。
- **FR-003（担い手）**:
  各返信の担い手は、候補の住民から、**特性にもとづく重みつきの決定論的サンプリング**で選ぶ。重みは次の要素の積:
  活動度と時間帯、記事との関連度、返信しやすさ（`ReplyTendency`）、スレッドの状態による補正。式は `plan.md` に定める。
  同じ記事の同じ返信番号には、同じ人が選ばれる。選ばれた人は、そのスレッドの直前の投稿者や、記事の著者自身（連続返信）にはならない。
- **FR-004（時刻）**:
  各返信の予定時刻は、親記事（または直前の返信）より後で、現在の世界時刻を超えない範囲で、重い裾のある遅延分布から決める。
  遅延は、担い手の活動パターンで尺度が変わる。
- **FR-005（関連度）**:
  記事と住民の関連度は、13 の興味領域（既存の `Persona.Interests` の語彙）の重みづけで計算する。記事の領域は、板の事前分布、
  NPC の記事に付く領域タグ、人間の投稿を辞書で照合した結果、のいずれかから得る。関連が薄い話題にも、一定の最小確率を残す。
- **FR-006（実体化）**:
  計画した返信は、予定時刻を過ぎたあとの観測（板の一覧、スレッド表示、定期更新）で、返信記事として実体化する。
  実体化は冪等で、同じ計画の返信が 2 回作られることはない。本文は、これまでどおり読まれたときに遅延生成する。
- **FR-007（永続化）**:
  計画は、担い手と予定時刻を含めて保存する。住民が増えても、保存済みの計画は変わらない。
- **FR-008（LLM を使わない）**:
  FR-001〜FR-007 の処理は、LLM のプロバイダを一切呼ばない。助言モデル（Jev）の結果にも依存しない。
- **FR-009（局の定義）**:
  板ごとの領域の重み、新人歓迎の性質のように、局固有の内容はプリセットの YAML で定義する（コードに局名や板番号を書かない）。
  定義がない板は、すべての領域を同じ重みとして扱う。
- **FR-010（文書の整合）**:
  `docs/WORLD_SIMULATION.md` の Jev の記述を、「この経路では使わない。接続されていない任意の助言機構」と明記する。
  `docs/BOARD_ACTIVITY_PLANNING.md` に、本数と担い手の関係を書く。

## 成功基準

- **SC-001**: 固定シードの統計テストで、領域への関心、活動パターン、`ReplyTendency`、スレ主の戻り、新人対応が、
  選択確率に、期待する向きの有意な差として現れる。
- **SC-002**: 反応の計画と実体化で、LLM プロバイダの呼び出しが 0 回（テスト用の偽プロバイダ）。
- **SC-003**: 同じ入力から、計画が常に同じ。実体化を繰り返しても、返信は増えない。
- **SC-004**: 既存の金型テスト（人物生成 `population_golden_test.go`、Erika-K の画面 `screens_golden.txt` など）が、
  1 バイトも変わらずに通る。人物の乱数の消費順序を変えない。
- **SC-005**: `go test ./...` が通る。

## スコープ外

- 助言モデル（Jev）の削除や改修。この経路で使わないだけで、コードは残す。
- 返信本文の生成方法、プロンプト、引用の選び方の変更。
- ペルソナの新しい項目の追加と、既存の人物データの再生成（乱数の消費順序は変えない）。
- 人物どうしの関係（友人、対立）のモデル。将来の拡張のための差し込み口（重み式の項）だけを用意し、値は常に 1 とする。
- 板・スレッドの閲覧履歴や既読状態の反映（ホストプログラムの領分）。
- 人間への私信（メール、チャット）への反応。
- 時間経過で、定期的に反応を計画するバックグラウンドの常駐処理。観測時の遅延評価だけを行う。
- 歴史的に確かな返信率・応答時間の主張。数値はすべて架空の調整値。
