# Spec: インタラクション台帳と主体識別の基盤（Interaction Ledger & Actor Identity）

**Spec ID**: 010-interaction-ledger  
**Status**: Draft  
**Depends on**: SDD-005（チャネル横断のインタラクション・フィードバック）P1〜P2

## 背景

現状のシステムでは、掲示板の書き込み、返信、メール、チャットなどの動的に発生した出来事が相互に影響する仕組みが不足している。実コードで確認した現状:

1. **人間の投稿の主体識別がない**:
   人間が板に投稿した際、`world.Post{Author: <handle>}` として保存されるだけで、会員ID（`AuthorMemberID`）もペルソナIDも持たない（`hostprogram/erikak/runtime.go`、`turbobbs/runtime.go`）。そのため、「誰が書いたか」を関係や観測の主体として追跡できない。
2. **チャネル横断の記録（台帳）がない**:
   記事は板ごとに保存されるだけで、チャネルやホストを越えて「誰が誰に何を言ったか」「どのやり取りが発生したか」を一元的に参照・導出する追記専用台帳（`InteractionEvent`）が存在しない。
3. **観測と関係が計算できない**:
   SDD-004 で定義された「誰がその投稿を知っているか（観測）」や「住民間の関係（接触回数、最終接触日時）」を計算する入力ソースがないため、spec 008 や後続の対話生成において関係を考慮できない（現在 spec 008 では関係項は常に 1 の固定値）。

本 spec は、SDD-005 の第1段階（P1: 主体の識別と台帳）および第2段階（P2: 観測・関係の派生）として、**人間とNPCを等しく扱う統一的なアクター識別と、掲示板投稿の追記専用台帳、および決定論的な関係エッジの導出基盤**を定める。

## 設計の原則

- **人間もNPCも同じ `ActorRef`。** 人間の会員を特別扱いせず、同じアクター識別子（`ActorRef: kind (persona|member), id`）で扱う（`AGENTS.md`「人間は世界の一員であり、主人公ではない」）。
- **台帳が真実、関係は導出キャッシュ。** すべての動的インタラクションは追記専用の `InteractionEvent` として記録する。関係（`RelationshipEdge`）は台帳から決定論的・冪等に再計算できる（`AGENTS.md`「PostgreSQL/world storage is canonical world truth」）。
- **決定に LLM を使わない。** 台帳の記録、観測判定、関係の更新はすべて数値計算と構造化データ処理のみで完結する（LLMプロバイダ呼び出し 0 回）。
- **確定した事実は変えない。** 一度コミットされた台帳イベントと投稿は書き換えない。

## ユーザーストーリー

### US1: 人間の投稿がアクターとして識別され、台帳に記録される（Priority: P1）

利用者が掲示板に新規投稿や返信を行った際、その投稿に会員IDが紐づけられ、システム共通のインタラクション台帳にイベントとして保存される。

**Independent Test**: 人間が記事を投稿すると、`world.Post.AuthorMemberID` が記録され、対応する `InteractionEvent` が台帳に1件追加される。アクターは `kind=member` として識別される。

### US2: NPC の投稿も同様に台帳に記録される（Priority: P1）

NPC が記事を投稿（またはバッチ実体化）した際、同様にペルソナIDをアクターとする `InteractionEvent` が台帳に記録される。

**Independent Test**: NPC の記事が保存された際、`world.Post.AuthorPersonaID` を元に `kind=persona` の `InteractionEvent` が作成される。

### US3: やり取りから関係エッジが決定論的に更新される（Priority: P2）

人間またはNPCがある記事に返信した際、返信元記事の著者と返信者の間に「関係エッジ（`RelationshipEdge`）」が更新され、接触回数（`interaction_count`）と最終接触日時（`last_interaction_at`）が記録される。

**Independent Test**: AがBの記事に返信すると、A→B の関係エッジの返信カウントが+1され、最終接触日時が更新される。同じイベントを重複して処理しても、カウントは二重加算されない（冪等性）。

### US4: LLM 呼び出しが 0 回（Priority: P1）

台帳記録と関係エッジ更新の全処理において、LLM プロバイダの呼び出しが一切発生しない。

**Independent Test**: テスト用偽プロバイダで呼び出し回数が 0 回であることを確認する。

## 要件

- **FR-001（アクター参照型）**:
  `world` パッケージに、NPCペルソナまたは人間の会員を一意に指す `ActorRef` 型（`Kind`: `"persona"` | `"member"`, `ID`: 文字列）を定義する。
- **FR-002（Post の会員ID拡張）**:
  `world.Post` に人間の会員IDを保持するフィールド `AuthorMemberID string` を追加する。人間が投稿する際は、セッションの会員IDがセットされる。
- **FR-003（インタラクション台帳イベント）**:
  `world` パッケージに `InteractionEvent` 型を定義する（イベントID、局ID、チャネル種別、アクター、公開スコープ、宛先アクター、応答元イベントID、参照コンテンツID、世界時刻）。
- **FR-004（投稿保存時の台帳追記）**:
  `Store.AddPost`（または関連リポジトリ）において、記事が保存された際に自動的・決定論的に対応する `InteractionEvent` を台帳に追記する。
  - ルート記事: `channel = "board_root"`, `addressed_to = []`
  - 返信記事: `channel = "board_reply"`, `addressed_to = [親記事の著者ActorRef]`, `responds_to_event_id` を設定
- **FR-005（関係エッジの導出）**:
  台帳イベントから、二者間の関係を表現する `RelationshipEdge` 型（`FromActor`, `ToActor`, `HostID`, `BoardReplyCount`, `LastInteractionAt`）を導出・保持する。返信が行われた際、返信者から被返信者への関係エッジを更新する。
- **FR-006（冪等性と決定性）**:
  台帳イベントおよび関係エッジの更新は、イベントIDにより冪等に処理される。同一イベントの再送や再計算によって関係カウントが二重加算されない。
- **FR-007（LLM 非依存）**:
  FR-001〜FR-006 の処理は、LLM プロバイダを一切呼ばない。

## 成功基準

- **SC-001**: 人間およびNPCの投稿から、正しいアクター型・スコープ・宛先を持つ `InteractionEvent` が生成・保存される。
- **SC-002**: 返信によって関係エッジのカウントと日時が正しく更新され、固定シード／同一入力から何度実行しても同じ結果が得られる。
- **SC-003**: 全処理で LLM 呼び出しが 0 回。
- **SC-004**: 既存の金型テスト（人物生成 `population_golden_test.go` や既存の画面出力等）が 1 バイトも変わらずに通る。
- **SC-005**: `go test ./...` が通る。

## スコープ外

- メールやチャットの永続化およびイベント追記（後続 Spec で実施）。
- エージェント記憶想起ツール（`StandardActorTools`）のバックエンド接続（後続 Spec で実施）。
- 好意・信頼・緊張などの心理パラメータの動的減衰計算（本 Spec では接触回数と最終接触日時の基盤のみを対象とする）。
- ペルソナの静的生成ロジックの変更。
