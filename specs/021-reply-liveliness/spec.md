# Spec: スレッドごとの盛り上がり（レス件数）を、話題・時間・人数を見て決める

**Spec ID**: 021-reply-liveliness  
**Status**: Draft  
**Depends on**: `main` に spec 008（`world.PlanReactions`、`world.ThreadReplyCount`）があること。`docs/LLM_POLICY.md` の
「Scope of LLM judgement (relaxed)」節（PR #380）があること

## 背景

利用者から、「データをリセットしても、板ごとのレスの付き方の傾向が毎回同じに見える」という指摘があった。コードで確認した事実:

1. レス件数は `world.ThreadReplyCount(hostID, boardID, ordinal, rate)` で決まる
   （`apps/server/internal/world/thread_replies.go`）。入力は、局 ID、板 ID、ルート記事の通し番号、板の `reply_rate` の 4 つだけ。
   乱数の代わりに、この 4 つの文字列の FNV ハッシュを使うため、**リセットしても、同じ板の同じ通し番号は必ず同じ件数**になる。
2. `reply_rate` は、局の定義（`hostcatalog/presets/*.yaml`）に板ごとに手書きされた値（hakata-canal-net では 0.20〜2.30）。
   未設定の板は、固定の 1.10（`bbsengine.effectiveBoardReplyRate`）。
3. 件数は、**記事の中身、投稿時刻、局の人数のどれも見ずに**決まる。件数を使う場所は 5 つあり
   （`bbsengine/engine.go` の `quotasForTotalSlotTarget`、`CatchUpInitialRootHistoryCount`、`CatchUpInitialBoardActivity`、
   `worldrepo/board_activity.go`、`world/reaction.go` の `PlanReactions`）、どれも同じ引数から同じ値を再計算している。
4. 初期生成では、ルート記事の話題（Situation）が決まる**前に**、件数の枠（quota）が決まる
   （`bbsengine.catchUp` が `planSlots`、`addThreadReplies` で全スロットを作り、そのあとに `Planner.PlanBBSBatch` で話題を作る）。

人間の感覚では、質問や相談は返信を呼びやすく、独白や告知は呼びにくい。夜のテレホーダイの時間帯は賑わい、会員数の少ない局では長いスレッドは成り立たない。
現状は、これらを一切反映できない。

`docs/LLM_POLICY.md` は、PR #380 で、LLM が世界の枠内で質的な判断（話題の盛り上がり、時間帯・人数の影響、スレッドの件数）をしてよいと改められた。
同じ入力から同じ活動を再現することは、目標でなくなった。この spec は、その方針を、レス件数の決め方に適用する。

## 設計の原則

- **世界が枠を決め、LLM が質的な判断をし、結果を世界の事実として保存する。**
  枠: 板の基準率、局の会員数と、その時刻に活動できる人数、投稿時刻、件数の上限。判断: その話題がどれだけ返信を呼ぶか。
- **LLM の判断は、数値の件数でなく、段階（盛り上がりの度合い）で受け取る。** 件数への換算は、世界が決まった式で行う。
  LLM は 3〜5 件のような無難な数に寄りやすく、長いスレッドと無反応のスレッドという重い裾の分布が失われるため。
- **再現性は目標でない。** 件数の抽選に、ハッシュでなく通常の乱数を使ってよい。ただし、**一度決めた件数は保存し、後から変えない**
  （観測された事実は黙って変わらない）。再計算でなく、保存した値を使う。
- **LLM が使えないときは止まらない。** 判断が得られなければ、基準の段階（中位）で、基準率から件数を決める。
- **人間の投稿を特別扱いしない。** 人間の投稿にも、NPC と同じ判断と同じ式を使う。
- 係数は架空の調整値で、歴史統計ではない。コードとドキュメントにそう明記する。

## ユーザーストーリー

### US1: リセットのたびに、スレッドの盛り上がりが変わる（Priority: P1）

運用者として、データをリセットして初期生成をやり直したとき、同じ板でも、どのスレッドが伸びるかが毎回変わってほしい。

**Independent Test**: 乱数源を差し替えて、同じ板・同じ通し番号で別の件数が出ること。固定の乱数源では、同じ件数になること。

### US2: 話題によって、盛り上がりが違う（Priority: P1）

利用者として、質問や相談のスレッドには返信が付きやすく、独白や告知には付きにくくあってほしい。

**Independent Test**: 偽の判断器が「盛り上がりやすい」と返した話題の件数の平均が、「盛り上がりにくい」と返した話題より、十分な回数の試行で有意に大きい。

### US3: 時間帯と人数が、盛り上がりに効く（Priority: P1）

利用者として、会員数の少ない局や、住民があまり活動していない時間帯に、長いスレッドが付かないでほしい。

**Independent Test**: その時刻に活動できる住民が 2 人のとき、件数が 2 を超えない（同じ人が連続で返信しない規則のもとで、現実に起こりうる最大）。
活動できる住民が多く、夜の時間帯のとき、昼より件数の期待値が大きい。

### US4: 判断が得られなくても、動き続ける（Priority: P2）

運用者として、LLM の障害時にも、板が空にならず、件数が基準率の近くに収まってほしい。

**Independent Test**: 判断器が常に失敗する偽実装で、件数の平均が基準率の近くになり、エラーで処理が止まらない。

## 要件

- **FR-001（盛り上がりの段階）**:
  各ルート記事に、**盛り上がりの段階** `reply_appeal`（整数 0〜4。2 が中位）を 1 つ付ける。LLM が判断し、短い理由（1 文）を添える。
  段階は記事の事実として保存し、後から変えない。
- **FR-002（判断の材料）**:
  判断器に渡す材料は、(a) 記事の話題の要約（確定済みの Situation の要約と件名）、(b) 板の名前と基準率 `reply_rate`、
  (c) 投稿の世界時刻（時刻、曜日）、(d) その時刻に活動できる住民の数と、局の会員数、(e) その板の直近のスレッドの件数（偏りを避けるため）。
  人物の私的な情報、他の局の情報は渡さない。
- **FR-003（件数への換算）**:
  件数は、世界が `reply_rate`、段階、活動できる人数、時刻から、決まった式で期待値を出し、乱数で抽選して決める。式は `plan.md` に定める。
  結果は、`[0, 上限]` に収める。上限は `world.MaxThreadReplies`（30）と、活動できる住民の数から決まる。
- **FR-004（保存）**:
  決めた件数と段階は、反応の計画（`world.ReactionPlan`）の一部として保存する。保存済みの計画があれば、再計算しない。
- **FR-005（既定への退避）**:
  判断器が使えない（未設定、失敗、期限切れ、不正な出力）ときは、段階を 2 として扱い、同じ式で件数を決める。
  この退避は、ログに記録する。処理は止めない。
- **FR-006（ハッシュの廃止）**:
  `ThreadReplyCount` の決定論的なハッシュは、乱数源を引数に取る形に変える。呼び出し元（5 か所）が、同じ記事について
  異なる件数を再計算しないよう、保存した値を使う。
- **FR-007（1 バッチ 1 回の判断）**:
  判断は、記事ごとではなく、1 回のバッチ（初期生成や定期の生成の 1 まとまり）で、複数のルート記事の段階をまとめて得る。
  LLM の呼び出し回数は、ルート記事の数に比例して増やさない。
- **FR-008（LLM 以外の入力の整合）**:
  人間の投稿に対する反応の計画（spec 008）にも、同じ判断と換算を使う。人間の投稿だけ別の倍率を持たせない。

## 成功基準

- **SC-001**: 乱数源を変えると、同じ板の同じ通し番号で、件数の列が変わる。同じ乱数源では、同じ列になる。
- **SC-002**: 偽の判断器の統計テストで、段階が高いほど、件数の期待値が大きい（単調）。
- **SC-003**: 活動できる住民の数が少ないとき、件数が上限を超えない。
- **SC-004**: 判断器が常に失敗しても、`go test ./...` が通り、件数の平均が基準率の近くに収まる。
- **SC-005**: 一度保存した計画の件数は、観測と再起動のあとでも変わらない。
- **SC-006**: LLM の呼び出し回数が、ルート記事の数ではなく、バッチの数に比例する（偽プロバイダの呼び出し回数で確認）。
- **SC-007**: `go test ./...` が通る。

## スコープ外

- 返信の**担い手**、**予定時刻**、**関連度**の決め方（spec 008 のとおり、LLM を使わない）。この spec が変えるのは、**件数**だけ。
- 返信本文の生成、プロンプトの変更。
- 話題ごとの盛り上がりやすさの表（YAML）の追加。判断は LLM に任せ、表は作らない。
- 既存のデータの再計算。すでに保存された計画と、観測された記事は変えない。
- 時間経過で、後から返信が増える仕組み（件数は計画時に確定する）。
- 歴史的に確かな返信率の主張。数値はすべて架空の調整値。
