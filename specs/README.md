# specs/

大きな変更は、コードを書く前に、ここに設計を書く。1 つの変更につき 1 つのフォルダ `NNN-name/` を作る。
実装は、人間でも、Copilot などのエージェントでも、この文書だけを読んで進められることを目標にする。

| 番号 | 内容 |
|---|---|

| 003 | generic-debug-names（HAKATA を含む名前の除去） |
| 004 | preset-population（住民の定義の外部化） |
| 005 | erika-k-station-detail（Erika-K の板構成と画面の文字列の外部化） |

## フォルダの構成

| ファイル | 役割 | 書くこと |
|---|---|---|
| `spec.md` | **何を、なぜ**。変えない点を含む | 背景、ユーザーストーリーと独立したテスト、要件（FR）、成功基準（SC）、**スコープ外** |
| `plan.md` | **どう設計するか** | 現状の分類、データの流れ、スキーマ、検証規則、検証（金型など）の方針、変更するファイル、リスクと対策 |
| `tasks.md` | **実行できる手順** | 作業のルール、番号付きのタスク（コマンド、挿入するコード、確認方法）、完了の定義 |
| `verification.md` | **実装した人が書く記録** | 実行したコマンドと結果（未実施は理由つき）、金型の根拠、手動確認 |

`tasks.md` は `templates/tasks.template.md` から作る。実装を依頼する文面は
`templates/implementation-request.template.md` を使う。

## 書き方の原則

過去の実装（003〜005）で、うまくいった点と失敗した点から決めた。

1. **数や名前は、実際のコードから数える。** 「26 件」と書いたが、実際は 29 件だった。件数、ファイル名、関数名は、
   読んだコードで確認してから書く。確認していないものは、タスクの中で「実際の値に直して報告する」と書く。
2. **変えてはいけない点を、検証できる形にする。** 「挙動を変えない」は、変更**前**のコードで記録した出力（金型）と、
   変更後の出力が、バイト単位で一致することで確かめる。金型は、実装より前にコミットし、後から作り直さない
   （実装後のコードから作った金型は、同義反復になり、何も証明しない）。
3. **成果物と完了の条件を、依頼文の先頭に書く。** 「spec に従って実装して」だけだと、「spec のファイルは既にあります」で
   終わることがある。完了の条件には、PR の差分に含まれるべきファイルを列挙する。
4. **スコープ外を、明示する。** やらないことを書かないと、親切な拡張が混ざる。
5. **コードは、挿入する位置まで書く。** 設計の意図だけでは、乱数の消費順序や空白のような細部が、再現されない。
   一方、コードを書いた部分は、コンパイルして確認していないことを、PR に書く。
6. **止まる条件を書く。** 同じ失敗が 2 回続いたら止まる。spec とコードが食い違ったら、推測せずに止まる。
7. **局固有の内容は、局の定義に置く。** ホストプログラムは、定義された文字列を出力するだけで、既定の文面を持たない
   （`AGENTS.md` の「Station-specific content lives in the station definition」）。

## 進め方

```text
設計（人間 + 設計担当）  →  spec / plan / tasks を書く  →  PR でマージ（main に入れる）
                                                              │
実装（エージェント）  ←  実装を依頼する（成果物を先頭に書く）  ←┘
        │
        ▼
draft の PR  →  レビュー（金型の履歴、スコープ、テスト）  →  CI（go-test）  →  手動確認  →  マージ
```

- spec のマージを先に済ませる。エージェントは `main` から作業するので、`main` に無い spec は読めない。
- エージェントの PR は、ワークフロー（`go-test`）が自動で動かないことがある。承認して実行するか、ローカルで確認する。
  CI の結果が無いものを、成功とみなさない。

## レビューの観点

1. 金型ファイルの履歴が 1 コミットで、実装より前にあるか（`git log --oneline -- <testdata>`）。
2. スコープ外のファイルや項目が、変更されていないか。
3. `tasks.md` が求めたテストが、揃っているか。
4. 局固有の文字列や名前が、ホストのコードに残っていないか（`grep -rniE "<局名>"`）。
5. `verification.md` が、実行したコマンドと結果を、正直に書いているか。
6. `go-test` の結果。
