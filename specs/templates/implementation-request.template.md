# 実装の依頼文のテンプレート

<!--
spec の実装を、Copilot などのエージェントに頼むときの文面。Issue の本文でも、セッションに入力するプロンプトでも、同じ。
<...> を埋める。「成果物」と「完了の条件」を、先頭に置くこと（`specs/README.md` の原則 3）。
前提: spec の PR が main にマージ済みであること。
-->

```
## 成果物（最初に読んでください）
この依頼の成果物は、**<Go / YAML / ... > のコードの変更（実装）**です。
`specs/<NNN-name>/` の spec・plan・tasks は、main に既にあります。
**spec のファイルを作る・変更することは、この依頼の仕事ではありません。**
「spec のファイルは既に存在するので、変更なし」は、完了ではありません。
<やり直しの場合: 前回の実装（#NNN）は <理由> のため閉じています。参考にしてよいですが、コピーせず、main から作り直してください。>

## 完了の条件（すべて満たすこと）
- PR の差分に、次のファイルが含まれていること:
  <パス>
  <パス>
  specs/<NNN-name>/verification.md
- <コードから無くなっているべきもの（例: 関数名、変数名、局名の文字列）>
- コミットの順序: <金型などの根拠のファイル>のコミットが、実装のコミットより前にあること。
  根拠のファイルは、変更前の main のコードで生成すること。

## 最重要（守れなければ、止まって報告してください）
- <変えてはいけない点（例: ○○の出力は 1 バイトも変えない）>
- 根拠のファイル（金型）は、tasks.md の T001〜T003 のとおり、実装の前に生成してコミットする。以降、更新用のフラグは使わない。
  金型のテストが失敗したら、実装が間違っている。金型を直さない。
- <この変更に固有の規則（例: 局の文字列は局の定義に書き、ホストは加工せずに出力する）>

## 読むもの（この順で）
1. AGENTS.md（特に「Implementing a spec」の節）
2. specs/<NNN-name>/spec.md
3. specs/<NNN-name>/plan.md
4. specs/<NNN-name>/tasks.md

## 作業
- tasks.md の T001 から T0XX を、番号順に実行する。「この作業のルール（必読）」に従う。
- スコープ外（spec.md 末尾）に手を出さない。
- .github/ 配下のファイルは変更しない。
- 実行していないコマンドを「成功した」と書かない。実行できなかったものは「未実施」と理由を書く。
- 同じテスト失敗を 2 回直して通らなければ、止めて、どの行が違うかを報告する。
- spec と実際のコードが食い違っていたら、推測で進めず、PR の説明に書いて止まる。

## 完了
- draft の PR を作る（tasks.md の最後のタスク）。説明に、根拠のファイルのコミットが実装より前であること、
  テストの結果、verification.md の内容を書く。
```

## 渡し方

- **Issue**: 上の本文で Issue を作り、Copilot に割り当てる。
- **セッション**: リポジトリを対象にし、ベースを `main` にして、上の本文をプロンプトに貼る。
- どちらでも、PR ができたら、`specs/README.md` の「レビューの観点」で確認する。
