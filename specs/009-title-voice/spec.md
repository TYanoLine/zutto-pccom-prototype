# Spec: 題名の書き方（書き手の声）の改善と、題名の形の診断

**Spec ID**: 009-title-voice  
**Status**: Draft  
**Depends on**: なし（spec 008 とは独立）

## 背景

本番の題名生成は、確定済みの出来事（Situation）から、一覧に出す root 件名を作る（`llm/situation_titles.go`、
`worldrepo/bbs_situation_first_planner.go` の `planSituationFirstRoots`）。Render の本番ログ
（`BBS generated content`、評価用ホストの 2026-10-02〜06、root 題名 179 件、11 板）を読んだところ、次の偏りが見つかった。
ベースラインは `specs/009-title-voice/baseline/root-titles-2026-10-02_06.jsonl` に保存してある
（変更前のコードが生成したもの。**目視による概数**。厳密な値は、T010 のツールで出す）。

| 観察 | 内容 |
|---|---|
| 対象名が先頭に集中 | ゲーム板 `20/1`（39 件）で、約 34 件が作品名・機種名から始まる。「X貸せます」「X買った人いますか」「Xで対戦しませんか」が反復する |
| 地名が先頭に集中 | 地域板 `10/1` は 10 件中 6 件、`10/2` は 10 件中 4 件が「天神」「地下街」から始まる |
| 同じ題材の反復 | クロノ・トリガーが 3 件、マリオRPG・ドラクエVI・マリオカート・バイオハザードが各 2 件ずつ、同一板内にある |
| 完全一致の題名 | 板 `3` に「開封した明太子の保存方法」が 2 件ある |
| 他の板は多様 | `60/*`、`70/1`、`3`、`1` は、用件・症状・状況から始まる題名が多く、固有名詞先頭は少ない |

**偏りは全体の癖というより、板の中心となる対象（作品名・地名）が題名の先頭に来る癖である。**

コードを読んで確認した、考えられる原因（仮説。実LLMでの検証は、T040 のリプレイで行う）:

1. 題名の呼び出しへの入力は、出来事の要約と事実の JSON である。ゲーム板の要約は「『スーパーマリオRPG』を遊び、〜」のように
   作品名から始まり、地域板の要約は日付や地名から始まる。題名の呼び出しは、これを短くする作業になり、語順が引き継がれる。
2. 題名の呼び出しの指示は、「短い件名」「36 文字以内・1 行・Re:なし」だけである。書き手の視点、文体、題名の型の幅についての材料がない。
3. 直近の root 題名の一覧を「文脈・重複回避の材料」として渡している。同じ型の題名が一覧に混ざると、次の呼び出しがそれを手本にする
   （同じ呼び出しの前のチャンクの題名も加わる）。
4. 題名の同一性の検査がなく、完全一致の重複が通る。
5. 指示に、作品名を先頭に付ける定型句を避ける記述がない（Lab 用の候補プール経路にだけ、地名先頭の定型句を避ける記述がある）。

一方、既存の方針（`docs/LLM_POLICY.md`）は次を定めている:
- 題名の対象が識別に必要なとき、作品名・製品名は題名に入れる（「Period-native conversational economy」）。
- 固有名詞のノルマや内容のテンプレートを作らない。
- 禁止事項の列挙を増やさず、**目的・素材・出力形式**で品質を改善する（「Prompt construction」）。

したがって、この spec は、対象名を題名から除くのではなく、**入力の素材を整え、LLM が自然に書き分けられるようにする**。

## 設計の原則（全体方針）

- **参照するが、限定しない。** 過去の事実、時代の傾向、既存の題名は、LLM が使う**素材**であり、書き方の上限ではない。
  素材を豊かにして LLM の力を引き出し、禁止・ノルマ・テンプレートで縛らない。
- **題名の型は、LLM が決める。** 世界側は、題名の型の割合を割り当てない。世界側が行うのは、素材の用意、決定論的な検証、
  複数案からの決定論的な選択、観測（診断）まで。
- **診断は、測るだけ。** 診断の指標は、生成を拒否する条件にしない。素材として LLM に事実を伝えることと、
  複数案からの選択に使うことだけを許す。
- **確定した事実は変えない。** 出来事（Situation）の要約・事実・正本には手を入れない。題名は言語化だけである。

## ユーザーストーリー

### US1: 題名の型が自然に多様になる（Priority: P1）

利用者として、板の一覧を縦に読んだとき、対象名や地名から始まる同じ型の題名が並ばず、実際の掲示板のように、
用件・感想・呼びかけ・近況・対象名などが混ざっていてほしい。

**Independent Test**: ベースラインの出来事（要約と事実）を入力として、新しい題名生成を複数回リプレイする（T040）。
ゲーム板・地域板で、先頭が対象名・地名である率が、ベースラインより下がる。

### US2: 対象名は、必要なときに題名に入る（Priority: P1）

利用者として、複数の作品が混在する板では、題名だけで何の話か分かってほしい。対象名が、題名のどこにあってもよい。

**Independent Test**: リプレイで、ゲーム板の題名の対象名の保持率（要約中の対象名が題名に含まれる率）が、ベースラインから大きく下がらない。

### US3: 題名の形を測れる（Priority: P2）

運用者として、題名の偏りを、数値で、いつでも確認したい。調整の前後で、効果を比較したい。

**Independent Test**: 開発用ツールにベースラインを与えると、先頭の語の型の率、末尾の反復率、完全一致の重複率、長さ、対象名の保持率が出る。

### US4: 同じ題名が並ばない（Priority: P2）

利用者として、同じ板に、まったく同じ題名が並んでいてほしくない。

**Independent Test**: 同一バッチまたは直近に完全一致の題名があると、その記事だけが 1 回再生成され、解消されない場合も、生成は失敗しない。

### US5: 方針が文書になっている（Priority: P2）

開発者として、「参照するが限定しない」という方針を、他の機能でも守れるよう、文書で確認したい。

**Independent Test**: `docs/LLM_POLICY.md` に、方針の節がある。

## 要件

- **FR-001（書き手の視点）**:
  題名の呼び出しは、「この人（ペルソナ）が、この板の一覧に、自分の投稿として付ける題名」という書き手の視点で書かせる。
  ペルソナの文体・年齢・職業など、すでに入力に含まれる素材（`persona_profile`）を、題名の素材として明示的に位置づける。
- **FR-002（要約の位置づけ）**:
  出来事の要約は、書き手が何をしたかを知る**背景**であり、語順や言い回しの手本ではない。この位置づけを、短く 1 回だけ書く
  （禁止事項を並べない）。
- **FR-003（例示）**:
  プロンプトに、題名の具体例を入れる場合は、対象の分野（ゲーム、地域など）の題名を使わない。例は、題名の型の幅を示す抽象的な記述にするか、
  無関係な分野のものにし、呼び出しごとに入れ替えられるようにする。ベースラインの題名をプロンプトに入れない。
- **FR-004（直近題名の渡し方）**:
  直近の root 題名は、**重複を避けるための題材の一覧**として渡し、題名の手本ではないことを示す。順序は、時系列ではなく入れ替えて渡す。
  あわせて、決定論的に測った**直近の形の事実**（例: 「直近の題名の約 6 割が対象名から始まる」「語尾が『貸せます』のものが 4 件ある」）を、
  事実として文章で渡してよい。ノルマや禁止ではなく、状況の説明とする。
- **FR-005（複数案と決定論的な選択。任意、既定は無効）**:
  設定で有効にすると、題名の呼び出しは、記事ごとに最大 3 案を、**構成の異なる**案として返す。世界側は、決定論的な規則
  （直近・同一バッチの題名との形の類似度が最も低い案。同点はハッシュ）で 1 案を選ぶ。
  すべての案が、既存の検証（36 文字以内、1 行、Re:なし）を通る。失敗時は、1 案だけの従来の動作に戻る。
- **FR-006（重複の検査）**:
  同一バッチと直近の root 題名に対して、正規化した完全一致の重複を検査する。重複した記事だけを最大 1 回、重複を伝えて再生成する。
  それでも重複する場合は、採用し（生成は失敗にしない）、診断に記録する。
- **FR-007（診断）**:
  次の指標を、決定論的に計算する純関数として提供する。ログ（既存の `BBS generated content` の周辺）と、開発用ツールで出力する。
  1. 先頭の語の型の率（対象名先頭、地名先頭、ハンドル先頭、それ以外）
  2. 末尾 4 文字の反復（最大シェア、上位）
  3. 完全一致・近似の重複率
  4. 文字数の分布
  5. 対象名の保持率（要約中の対象名が題名に含まれる率）
  診断は、生成の可否に使わない（FR-005 の選択と、FR-004 の事実の文章化に使うことだけを許す）。
- **FR-008（正本の不変）**:
  出来事の要約、事実、`Intent`、人物事実、本文の生成には、変更を加えない。変わるのは、題名の文字列と、その生成に使うプロンプト・入力だけである。
- **FR-009（文書）**:
  `docs/LLM_POLICY.md` に「参照するが限定しない」の節を足す。`AGENTS.md` は変更しない（設計ルールの変更は、人間が判断する。提案文は PR の説明に書く）。

## 成功基準

評価は、保存済みの出来事（ベースライン）を、実 LLM でリプレイして行う。値は**評価の目安**であり、実行時に強制する制限ではない。

- **SC-001**: ゲーム板 `20/1` で、先頭が対象名である率が、ベースライン（約 87%）より有意に低く、目安は 65% 以下（3 回以上のリプレイの平均）。
- **SC-002**: 地域板 `10/1`、`10/2` で、「天神」「地下街」から始まる率が、ベースライン（`10/1` で 6/10、`10/2` で 4/10）から、目安として半減する。
- **SC-003**: 同じ末尾 4 文字の最大シェアが、ベースラインより下がる。
- **SC-004**: ゲーム板の対象名の保持率が、90% 以上（ベースラインはほぼ 100%）。題名だけで何の話か分からなくなっていない。
- **SC-005**: リプレイの題名に、完全一致の重複が 0 件。
- **SC-006**: 36 文字以内、1 行、Re:なし、という既存の検証が、すべての題名で通る。
- **SC-007**: コスト。複数案を無効にした場合、題名の呼び出しの入力トークンの増加が +10% 以内。有効にした場合、出力トークンの増加が +50% 以内。
- **SC-008**: 既存のテストが、変更なしで通る。LLM を呼ばない部分（診断、選択、重複検査、プロンプトの組み立て）は決定論的で、テスト用の偽プロバイダで検証される。

## スコープ外

- 出来事（Situation）を提案する側のプロンプトと、要約の書き方（`openai_world_situation_proposer.go`）。語順の主な原因は、
  要約が対象名から始まることにある可能性がある。**本 spec の効果が不十分なら、後続の spec で扱う**（plan の「フォローアップ」）。
- 本文の生成、返信の件名、引用、人物生成。
- Lab 用の候補プール経路（`bbs_title_candidates.go`）のプロンプトの変更。ただし、その審査のプロンプトの例示に、ゲームの題名が含まれることは、
  衛生上の課題として PR の説明に書き、後続とする。
- 題名の文字数の上限（36）の変更。
- 固有名詞のノルマ、題名の型の割合、内容のテンプレートの導入（禁止）。
- 歴史検証（Historical KB）と、Era 検証。
- 他のホストへの個別対応。評価用ホスト以外でも同じ入力で動くが、ベースラインは評価用ホストのものだけである。
