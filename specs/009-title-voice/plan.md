## 2. 設計

### 2.1 プロンプトの構成（目的・素材・出力形式）

禁止事項を増やさず、次の 3 部にする。文面は、**骨子**である。最終の文言は、T040 のリプレイで確かめる。

1. **目的**（1〜2 文）: 「ずっとパソコン通信」の内部生成。確定済みの出来事を、**その人物が、自分の投稿として、板の一覧に付ける題名**にする。
   題名は、一覧を眺める人に、この投稿を開くかどうかを決めさせる、短い言葉である。
2. **素材**（構造化して渡す）:
   - `board`（名前、範囲）、`world_date`、局・地域
   - `author`（ハンドル、`persona_profile`。文体・年齢・職業を含む）
   - `background`（出来事の要約と事実）。**「書き手が何をしたかを知る背景。語順や言い回しの手本ではない」**と、1 回だけ書く（FR-002）
   - `already_covered`（題材の重複を避けるための一覧。順序は入れ替え。手本ではない）（2.3）
   - `recent_form_facts`（直近の形の事実。任意。2.3）
   - `form_notes`（題名の幅を示す例。話題の手本ではない）（2.2）
3. **出力形式**（スキーマ）: 36 文字以内、1 行、`Re:` なし。複数案を有効にしたときは、最大 3 案（2.5）。

現在の入力は、`canonical articles` の 1 つの JSON に、persona、要約、事実が混在している。これを `author` と `background` に分けて、
書き手の素材（persona）が要約より先に来る順序にする。フィールド名 `situation_summary` を `background` に改める（出力には影響しない）。

### 2.2 例示（FR-003）

- プロンプトの例は、`form_notes` として、**対象の分野と無関係な、1996 年前後の日常**の題名（園芸、料理、鉄道、読書など）から、
  題名の型の幅（用件から、近況から、呼びかけから、感想から、対象名が末尾、省略形、助詞止め、など）を示す。
- 例の候補は、データ（Go のデータ表または YAML）として 8〜12 個持ち、呼び出しごとに、`hash(host|board|batch)` で 3 個を選ぶ。
- 例には、現代語を含めない（`AGENTS.md` の In-world writing）。ゲーム・地域の題名は入れない。ベースラインの題名を入れない。
  テストで、プロンプトにベースラインの題名が含まれないことを確かめる。
- 例は、解釈のテストであり、内容のテンプレートではない（`docs/LLM_POLICY.md` の既存の記述に従う）。

### 2.3 直近題名の渡し方（FR-004）

- `already_covered`: 直近の root 題名（既存の `recentSubjects`）を、**シード付きで入れ替え**、最大 20 件にして渡す。見出しは、
  「すでに扱った題材（重複を避けるための一覧。語順や言い回しの手本ではない）」。
- `recent_form_facts`: `titleshape` が測った直近の形から、事実の文を作る。例: 「直近 20 件のうち、対象名から始まるものが 13 件」。
  ノルマや禁止の語を含めない。**事実だけ**。偏りが小さいとき（しきい値以下）は、空にする（材料を増やさない）。
  しきい値は、定数にまとめ、「調整値」とコメントする。

### 2.4 診断（`internal/titleshape`、新規。純関数）

| 指標 | 定義 |
|---|---|
| 対象名の抽出 | 要約中の『…』で括られた語（作品名など）。なければ、要約の先頭の、カタカナ・英数字の連続（2 文字以上） |
| 先頭の型 | 正規化（NFKC、空白・中点の除去）した題名が、(a) 抽出した対象名のいずれかで始まる → `referent`、(b) 地名の語（呼び出し側が渡す。板の範囲・地域から取る）で始まる → `place`、(c) ハンドル様の英大文字・数字・`.` の連続で始まる → `handle`、(d) それ以外 → `other` |
| 末尾の反復 | 終端記号（`？`、`！`、`?`、`!`、`…`、`。`）を除いた末尾 4 文字の出現数。最大シェアと上位 |
| 重複 | 正規化した完全一致。近似は、文字 2-gram の Jaccard ≥ 0.8 |
| 長さ | 文字数の最小、中央値、最大 |
| 対象名の保持率 | 要約から対象名が抽出できる記事のうち、題名に対象名（正規化後）を含むものの率 |

- 診断は、`BBS title shape: {…}` の JSON 1 行で、バッチごとに出力する（`shouldLogGeneratedContent` と同じ条件）。
- 開発用ツール `cmd/titlestats`: `BBS generated content` の JSONL（ベースラインと同じ形式）を読み、板ごとに指標を出す。
  地名の語は、`--places 天神,地下街,博多駅` で与える（省略時は、板の範囲から取れる語がなければ `place` を数えない）。

### 2.5 複数案と決定論的な選択（FR-005。既定は無効）

- 設定が有効なとき、出力スキーマは `titles: {event_id: [string, string?, string?]}`（1〜3 案）にし、プロンプトに
  「構成の異なる案を、記事ごとに最大 3 案」と書く。無効なときは、従来どおり文字列 1 つ。
- 選択の規則（`titleshape.PickVariant`）:
  1. 各案の、`already_covered` と、同じバッチですでに選んだ題名に対する**最小の形の距離**を求める。
     距離 = `1 − (0.4·先頭 3 文字の一致 + 0.4·末尾 4 文字の一致 + 0.2·文字 2-gram の Jaccard)`。
  2. 最小距離が最大の案を選ぶ。同点は `hash(host|board|event|案番号)` の小さい順。
  3. 検証を通らない案（36 文字超過など）は、候補から除く。全案が通らなければ、従来のエラー（呼び出しの失敗）。
- この選択は、LLM の案を**選ぶ**だけで、題名の型を割り当てない。重みや係数は、定数にまとめ、「調整値」とコメントする。

### 2.6 重複の検査（FR-006）

1. 各チャンクの題名を受け取ったあと、正規化した完全一致を、`already_covered` と、そのバッチのこれまでの題名に対して調べる。
2. 重複した記事だけを集め、`already_covered` に重複した題名を足し、同じ呼び出しで再生成する（最大 1 回）。
3. 再生成後も重複していれば、そのまま採用する。診断に `duplicate_accepted` として記録する。失敗にしない。

### 2.7 設定

- 複数案は、既存の設定（`internal/config/config.go`）の流儀で、環境変数 1 つ（既定は無効）。
- 診断のログは、既存の `debug.content_log`（ホストの定義）に従う。ホスト ID や電話番号で分岐しない。

## 3. 検証の方針

- **ベースライン**: `baseline/root-titles-2026-10-02_06.jsonl`（変更前のコードが本番で生成した 179 件。コミット済み）。ここから指標を出す（T010）。
  厳密な値は、このツールの出力で `verification.md` に記録する。この文書の概数（約 87% など）は、目視であり、ツールの値で置き換える。
- **決定論的な部分**: `titleshape`（診断、距離、選択）、重複検査、プロンプトの組み立て（偽のプロバイダが受け取ったプロンプトを検査）。
  既存の金型はない。ベースラインの指標は、**範囲で**検証する（実装後のコードから金型を作らない）。
- **リプレイ（実 LLM）**: `cmd/titlereplay`。ベースラインの出来事を入力として、新しい題名生成を `--runs 3` 以上で実行し、`titlestats` で比較する（SC-001〜SC-007）。
  API キーがなく実行できない場合は、「未実施」と理由を `verification.md` に書く。CI には入れない。
  - 制限: ベースラインには、`persona_profile` と、生成時の直近題名がない。リプレイは、persona なし、直近題名は、リプレイ内で積み上げたもので代替する。
    本番との差を `verification.md` に書く。
- **コスト**: 題名の呼び出しのトークン使用量を、`storeDevelopmentPlanningUsage`（`bbs-situation-title`）で比較する。

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| 題名が、対象不明の抽象的な題名になる（「おすすめありますか」化） | 対象名の保持率（SC-004）を、リプレイで測る。素材の説明に「複数の対象が混在する板では、題名だけで何の話か分かること」を 1 回書く（既存方針に沿う） |
| 要約が対象名から始まる影響が大きく、題名のプロンプトだけでは効果が出ない | SC-001 が満たせない場合、フォローアップ（6 章）。測ってから判断する |
| 直近の形の事実が、新たな偏りの手本になる | しきい値以下のときは渡さない。リプレイで、事実あり・なしを比べる |
| 複数案でトークンが増える | 既定は無効。SC-007 の範囲で、有効にするかを、測ってから決める |
| 診断の対象名の抽出が弱い（『』のない要約） | 先頭のカタカナ・英数字の連続で補う。保持率は、抽出できた記事だけで計算する。限界を `verification.md` に書く |
| ベースラインとリプレイの入力の違い | 制限を明記し、本番での再測定（ログ）を、完了後の確認に入れる |

## 6. フォローアップ（本 spec のスコープ外）

1. **Situation の提案側**: 要約（`occurrence`、`post_content`）を、書き手の声・語順に近い形で提案させる。
   題名の語順の原因が、要約の語順にある場合の根本対応。SC-001 が満たせないときに、別の spec で扱う。
2. Lab 用の候補プール経路の審査プロンプトの例示に、ゲームの題名（「クロノ・トリガーを今さら始めました」ほか）が含まれる。
   例示の模倣を避けるため、分野外の例へ置き換える（衛生）。
3. 返信の本文・件名への展開。

## 実装時に確認すること

- `BBSSituationTitleSeed` の `persona_profile` が、本番で実際に入っているか（ベースラインのログには出ていない）。
- 地名の語を、板の範囲・地域から機械的に取れるか。取れない場合の、ツールの `--places` の運用。
- 構造化出力のスキーマ（`responseTextWithJSONSchema`）が、文字列と配列の併用を許すか。許さない場合は、スキーマを 2 つ持つ。
- `rootSubjects(req.RecentPosts)` の件数と順序（現在の上限）。
