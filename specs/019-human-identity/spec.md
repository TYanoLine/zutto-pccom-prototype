# Spec 019: 人間の識別子 (human-identity)

## 1. 概要

人間の利用者を、システムの中で一貫して 1 つの識別子（**人間 ID**）で扱う。ゲストも含む。

- **システムは人間 ID で記録する。** 書き込み、チャットの発言、電報、回線の占有、台帳の主体は、すべて同じ人間 ID になる。
  あわせて、その記録のときに表示されていた**ログイン ID**も残す。
- **住民（AI）は人間をログイン ID でしか知らない。** 住民の知り合いの判定、関係、出来事の話題、行動の記憶は、ログイン ID で行う。
  人間 ID は、住民の材料にも LLM のプロンプトにも現れない。

これで、次のことが起こりうる世界になる（PR #360 のコメント）。

- ゲストでチャットした人が、あとで別の ID で入って「あのときの GUEST です」と名乗る。住民は、名乗られるまで同じ人だと分からない。
- 1 人が複数の ID を使い分けたり、他人の ID を名乗ったりする。システムは同じ人だと分かるが、住民には別の人に見える。

本仕様は識別子の土台であり、入会登録やパスワードの照合は作らない（§8）。

## 2. 背景と課題

1. **人間の識別子が 2 種類あり、食い違う。**
   - 書き込みは、入力したハンドルで記録される（`erikak/runtime.go` の `Author: r.handle, AuthorMemberID: r.handle`）。
     ゲストは全員 `member:GUEST` になり、区別できない。
   - チャットの発言、電報、回線の占有は、接続ごとの乱数の ID（`ws` の `CallSession.ID`）で記録される（`member:<通話 ID>`）。
     同じ人でも、かけ直すたびに別人になる。
   - `world/presence.go` のコメントは「会員のアカウントができるまで、ID は通話 ID」と書いている。
2. **橋渡しが仮のもの。** spec 017 の実装（PR #360）は、チャット室の人間と書き込みを結びつけるため、`worldrepo/chat_talk.go` に
   `memberAliases`（`member:<ハンドル>` を部屋の `member:<通話 ID>` と同じ人として扱う対応表）を置いた。コメントに
   「人間のシステム上の識別子は別の変更」と書いてある。
3. **人間を続けて識別する手段がない。** サーバはクッキーも認証も読まない。ブラウザが保存しているのは世界のカタログの鍵
   （`zutto.worldKey.v1`）だけで、それは利用者ではなく世界を識別し、通話には渡されない。
4. **人間 ID とログイン ID の区別が文書にない。** `docs/research/ACCOUNT_ID_HANDLE_EVIDENCE.md` は住民について
   「世界内の人物のキー」「局のログイン ID」「ハンドル」の 3 つを分けているが、人間の利用者には当てはめていない。
   `docs/ARCHITECTURE.md` の既知の近道に「人間の書き込みはハンドルの文字列だけで記録される」とある。

## 3. 決定事項

- 人間 ID は、人間 1 人（ブラウザ 1 つ）につき 1 つ。ゲストも、ログインする前から人間 ID を持つ。世界（カタログの鍵）をまたいで同じ。
- 人間 ID はブラウザが保存する**呼び出し元の鍵**から、サーバが求める。鍵そのものは記録に残さない。
  鍵を送らない（または形の正しくない鍵を送った）接続は、その通話だけの人間 ID になる。
- 住民にとっての人間は「その局のログイン ID」。システムの主体の欄（`ActorRef`）の種類 `member` は人間 ID を指すように意味を改め、
  住民から見た人を表す種類 `login` を新しく置く（`login:<ログイン ID>`、局はその記録の局）。
- **ゲストのログイン ID（`GUEST`）は、住民の知り合いにならない。** 誰が GUEST かは住民には分からないので、GUEST との関係は数えず、
  GUEST の書き込みを出来事の話題にしない。部屋の中で「GUEST」と呼んで応じることはこれまでどおりできる。
- ログイン ID の比較は、ホストプログラムが記録した文字列の完全一致とする（大文字小文字の規則は局ごとに未決定のため、共通の層で正規化しない）。
- 古い記録（`member:<通話 ID>`、`member:<ハンドル>`、人間 ID のない書き込み）は書き換えない。住民から見た人は、記録に残ったログイン ID で求める。

## 4. ユーザーストーリー

1. **かけ直しても同じ人（共通）。** 同じブラウザから 2 回接続すると、2 回の通話の回線の占有、チャットの発言、電報、書き込みが同じ人間 ID で記録される。
   - 独立したテスト: 同じ呼び出し元の鍵で 2 回 `dial` すると、2 つの通話の `HumanCall.HumanID` が等しく、通話 ID は異なる。
     別の鍵では人間 ID が異なる。鍵がなければ、通話ごとに異なる。
2. **ゲストも同じ人（共通）。** GUEST で書き込み、チャットで発言すると、それぞれ人間 ID とログイン ID `GUEST` の両方が記録される。
   別のブラウザのゲストとは人間 ID が異なる。
   - 独立したテスト: 2 つの鍵でそれぞれ GUEST として書き込むと、2 つの書き込みの `AuthorHumanID` が異なり、`Author` はともに `GUEST`。
3. **住民はログイン ID でしか知らない（共通）。** 人間 A が TARO で住民の書き込みにレスをつけ、その後 GUEST でチャット室に入ると、
   その住民にとって部屋の人は初対面（関係 0）。TARO で入ると、関係がある。人間 B が TARO を名乗って入っても、住民にとっては TARO との関係がある。
   - 独立したテスト: 上の 3 つの場合で、チャット室の枠の計算に渡る関係の値が、それぞれ 0、1 以上、1 以上になる。
4. **出来事の話題もログイン ID（共通）。** spec 017 の `news` の枠は、部屋の人と同じログイン ID の書き込みについてだけできる。
   同じ人間 ID でも、違うログイン ID の書き込みは話題にならない。GUEST の書き込みは話題にならない。
   - 独立したテスト: 人間 A が TARO で書き込み、GUEST で部屋に入ると `news` の出来事が 0 件。TARO で入ると 1 件以上。
5. **人間 ID は住民の材料に出ない（共通）。** チャットの 1 行の生成、記事の本文の生成、行動の記憶の検索結果の材料に、人間 ID が現れない。
   - 独立したテスト: 試験用の生成器が受け取ったリクエストを JSON にした文字列に、人間 ID が含まれない。行動の記憶の検索結果にも含まれない。
6. **自分の判定は通話で（絵理香K版）。** 同じ人が 2 つの通話を同時にしても、WHO と回線の一覧で「自分」は自分の通話の回線だけになり、
   同じ部屋にいるもう一方の通話の発言は、他の人の発言として表示される。
   - 独立したテスト: 同じ人間 ID の 2 つの通話がある状態で、一方の画面の WHO で自分の印が 1 行だけ付く。
     同じ部屋で一方が発言すると、もう一方の画面にその行が出て、発言した側の画面には二重に出ない。
7. **古い記録が読める（共通）。** 人間 ID の欄のない古いスナップショットがそのまま読め、そこに残った人間の書き込みと発言は、
   記録されたログイン ID で住民に知られる。
   - 独立したテスト: 新しい欄のないスナップショットを読み込み、古い書き込みの住民から見た人が `login:<Author>` になる。

## 5. 要件（FR）

### 人間 ID（共通）

- **FR-001（呼び出し元の鍵）**: Web の端末は、初回に乱数 128 bit の鍵（32 桁の小文字 16 進）を作って `localStorage` に保存し
  （世界の鍵と同じ扱い。保存できなければそのページの間だけ使う）、`dial` のメッセージで送る。`resume` では送らない（通話がすでに持つ）。
- **FR-002（人間 ID の導出）**: サーバは、形の正しい鍵から、鍵を含まない人間 ID を決定論的に求める（一方向の要約）。
  鍵がない、または形が正しくないときは、その通話だけの乱数の人間 ID を作る。鍵はログにも記録にも残さない。
- **FR-003（通話）**: `HumanCall` と人間の `PresenceSession` は、主体を `member:<人間 ID>` にし、通話 ID を別の欄に持つ。
  ホストプログラムには、通話 ID、人間 ID、回線、速度をまとめて渡す。

### 記録（共通）

- **FR-004（書き込み）**: 人間の書き込みは、人間 ID（新しい欄）と、そのときのログイン ID（`Author` と `AuthorMemberID`）の両方を持つ。
  `AuthorMemberID` は「局のログイン ID」の意味のまま残す。
- **FR-005（チャットの発言・電報）**: 人間の `ChatUtterance.Actor` と `LineMessage.From` は `member:<人間 ID>`。
  ログイン ID は `ChatUtterance.Handle` と、`LineMessage` の新しい欄（送り手のログイン ID）に残す。
- **FR-006（台帳）**: 人間が主体の `InteractionEvent` は、`Actor` を `member:<人間 ID>` にし、新しい欄に主体のログイン ID を持つ。
  宛先が人間のときも、宛先のログイン ID を持つ。古い書き込み（人間 ID なし）の主体は、これまでどおり `member:<AuthorMemberID>`。

### 住民から見た人（共通）

- **FR-007（住民から見た人）**: 主体とログイン ID から「住民から見た人」を求める共通の関数を 1 つ置く。
  住民はそのまま、人間は `login:<ログイン ID>`。ログイン ID が `GUEST` のときは「知り合いにならない人」を表す値を返す。
- **FR-008（関係）**: 掲示板の返信から作る関係（`RelationshipEdge`）の人間の側は、住民から見た人で記録する。GUEST の側の関係は作らない。
  住民同士の関係は変えない。
- **FR-009（チャット室）**: spec 017 の関係の値と `news` の出来事は、住民から見た人で求める。`memberAliases` と、それを受け取る引数をなくす。
- **FR-010（行動の記憶）**: 行動の記憶（spec 011）の検索で、人間は `login:<ログイン ID>` として現れ、相手の指定にも `login:<ログイン ID>` を使える。
  人間 ID は検索結果に出ない。
- **FR-011（材料）**: LLM に渡すすべての材料（チャットの 1 行、記事の本文）で、人間はログイン ID だけで表す。

### ホストプログラムでの具現化

- **FR-012（絵理香K版）**: 書き込み（新規と追記）に人間 ID を入れる。電報の送り手は `member:<人間 ID>` とログイン ID。
  自分の判定は、人間 ID ではなく自分の通話で行う。WHO と回線の一覧は通話 ID（`PresenceSession` の新しい欄）で、部屋の発言はこの通話で記録した発言の ID で判定する。
  チャット室の人間の在室（spec 017 の `EnterChatRoom` / `LeaveChatRoom`）は通話ごとに数える。画面の文字列は変えない。
- **FR-013（TurboBBS）**: 通話の情報を受け取り、書き込みに人間 ID を入れる。画面と局内のアカウントの扱いは変えない。

### 文書

- **FR-014**: `docs/WORLD_SIMULATION.md` に人間 ID とログイン ID の区別と「住民はログイン ID でしか知らない」ことを書く。
  `docs/ARCHITECTURE.md` の既知の近道の「人間の書き込みはハンドルの文字列だけ」を直す。`world/presence.go` のコメントを直す。
  `docs/research/ACCOUNT_ID_HANDLE_EVIDENCE.md` に、人間の利用者への当てはめを短く加える（プロジェクトの仕様として。史実の主張にしない）。

## 6. 成功基準（SC）

- SC-001: §4 の各ストーリーの独立したテストが通る。
- SC-002: 絵理香K版の画面の金型（`erikak/testdata`）と人物生成の金型（`world/testdata`）が 1 バイトも変わらない。
- SC-003: 人間 ID が、LLM のリクエスト、行動の記憶の検索結果、端末に出る文字列に現れない（テストで確かめる）。
- SC-004: 呼び出し元の鍵が、ログ、記録（スナップショットの JSON）に現れない（テストで確かめる）。
- SC-005: `go -C apps/server test ./... -count=1`、`go -C apps/server vet ./...`、`go -C apps/server test -race ./internal/worldrepo ./internal/ws`、
  Web の型検査とテストが通る。

## 7. 不変条件

- システムの記録の人間の主体は、人間 ID だけ。通話 ID やハンドルを人間の主体にしない（古い記録を除く）。
- 住民の判断と LLM の材料に、人間 ID を使わない。住民は人間をログイン ID で区別する。
- 人間の記録には、そのときのログイン ID が残る。あとからログイン ID を書き換えない。
- GUEST は住民の知り合いにならない。
- 記録した事実は書き換えない。古い記録を新しい形に移し替えない。

## 8. スコープ外

- 入会登録、パスワードの保存と照合、ログイン ID の重複の禁止・文字種の検査、ハンドルとログイン ID の分離。
- 人間 ID による本人確認（鍵を他のブラウザに写せば、同じ人になる）。複数の端末で同じ人になる方法。
- 住民が「あのときの GUEST です」のような名乗りを理解して、2 つのログイン ID を同じ人と覚えること（今後の記憶の仕様）。
- 台帳と関係の永続化（現在はスナップショットに入っていない）。
- 人間 ID ごとの集計・管理の画面、ログイン ID ごとの利用制限（BAN など）。
- 回線宛メッセージへの返信と住民からのメッセージ（spec 018）。
- 絵理香K版と TurboBBS 以外のホストプログラム。
