# Spec: Erika-K の記事番号を板ごとの連番にし、アペンドには記事番号を振らない

**Spec ID**: 020-erika-k-article-numbering
**Status**: Draft（未決事項あり。`## 未決事項` を参照）
**Depends on**: `docs/host-programs/erika-k.md` の「Article numbering and append rules」（PR #369、マージ済み）、spec 005（局の板構成の外部化）

## 背景

Erika-K（`apps/server/internal/hostprogram/erikak/runtime.go`）は、記事の番号に店舗全体の通し ID（`world.Post.ID`）をそのまま使っている。

- 板の一覧（`renderBoardIndex`）は `p.ID` を `%4d` で表示する。
- 投稿完了時の `MSG No.%d を登録しました` も `p.ID` を使う。
- アペンド（`append_body`）も同じ `AddPost` を通るため、通し番号を消費する。
- 番号による指定（`BR n`、`A n`）は `rootPost(id)` で、通し ID を引いている。

その結果、板 01 の一覧に `2050, 2052, 2054, 2059` のように番号が飛び、アペンドや他の板の投稿が番号を消費する。
これは `docs/host-programs/erika-k.md` の仕様（板ごとの独立採番、アペンドは記事番号を持たない）と食い違う。

仕様は次の 3 点である（根拠の強さは仕様書に記載）。

1. 記事番号は板ごとに 1 から採番する。
2. 削除された記事の番号は欠番として残し、詰めて振り直さない。
3. アペンドには記事番号を振らない。アペンドの内部 ID は記事番号と別に持つ。

## ユーザーストーリー

### US1: 板の一覧と投稿の番号が、板ごとの連番で表示される（Priority: P1）

利用者として、板を開いたときの番号が、その板の中で 1 から続く番号であってほしい。
他の板やアペンドの投稿で番号が飛ぶと、板の中の記事数が分からなくなるため。

**Independent Test**: 2 つの板に記事を書き込み、それぞれの一覧の番号が、板ごとに連続していることを確認する。
アペンドを書き込んでも、一覧の番号が変わらないことを確認する。

### US2: 番号で記事を指定すると、同じ板の記事が開く（Priority: P1）

利用者として、一覧で見た番号を `BR n` や `A n` に入れると、その板の記事が開いてほしい。

**Independent Test**: 板 A の番号 5 を `BR 5` で開くと板 A の記事 5 が出る。板 B に同じ番号 5 があっても、板 A の一覧から開いたときは板 A の記事を指す。

### US3: アペンドは記事番号を消費しない（Priority: P1）

利用者として、アペンドを書いても次の記事の番号が増えないでほしい。
アペンドは親記事の下に並ぶもので、独立した記事ではないため。

**Independent Test**: 板に記事 1 を書き、アペンドを 3 件書き、次の記事を書く。次の記事の番号は 2 になる。

### US4: HAKATA の既存の画面は、番号以外が変わらない（Priority: P1）

運営者として、この変更で変わるのは番号の表示だけであることを、自動テストで確認したい。
板の表、画面の文字列、コマンドの応答は、変更前と 1 バイトも違ってはならない。

**Independent Test**: 変更前のコードで記録した出力（金型）と変更後の出力を比べ、差分が番号の列だけであることを確認する。

## 要件

- **FR-001（板ごとの採番）**: Erika-K の記事（`ParentID == 0` の投稿）は、板ごとの記事番号（以下「記事番号」）を持つ。
  記事番号は板の中で 1 から連続する。板の間で番号を共有しない。
- **FR-002（生成された過去の記事）**: 板の活動計画（`BoardActivityState`）から生成された記事は、
  その板の計画上の番号（`TotalRoots` からの連番。`plan.md` の「番号の割り当て」）を持つ。
  生成された記事の番号は、その記事の返信の数の計算（`ThreadReplyCount`）で使う順番と一致する。
- **FR-003（人間の記事）**: 利用者が書いた記事は、その板の記事番号の最大値（生成された記事の計画上の番号を含む）の次の番号を持つ。
- **FR-004（削除と欠番）**: 記事番号は一度割り当てたら変えない。記事を削除しても、その番号は再利用しない。
  本仕様では削除の操作を追加しない。削除の操作が将来入るときは、番号を保存してから消すこと（`plan.md`）。
- **FR-005（アペンド）**: アペンドは記事番号を持たない。アペンドの内部 ID は、記事の内部 ID と同じ採番器から取る。
  アペンドが記事番号の採番を進めないこと。
- **FR-006（番号による指定）**: `BR n` と `A n` の `n` は、現在の板の記事番号で解決する。
  解決できないときは既存の「そのMSGはありません」を出す。
- **FR-007（表示の変更）**: 板の一覧の番号列と、`MSG No.%d を登録しました` の番号は、記事番号を表示する。
  アペンドの表示（`アペ 1`、`アペ 2`）と、一覧の `ap/ref` 列の数え方は変えない。
- **FR-008（保存データ）**: 記事番号は記事と一緒に保存される。保存データに記事番号が無い記事（本仕様より前の記事）の扱いは
  `## 未決事項` の 1 で決める。
- **FR-009（他の局・他のプログラム）**: 他のホストプログラム（TurboBBS、VS、bbsengine など）の番号は変えない。
  `world.Post` の共通の型への変更は、Erika-K の記事番号を入れるための、後方互換な任意フィールドだけに限る。
- **FR-010（金型）**: 変更前のコードで、HAKATA の板の一覧、投稿と返信の表示、番号による指定の応答を金型として記録する。
  変更後、金型との差分は番号の列に限られる。

## 成功基準

- **SC-001**: US1〜US3 の Independent Test が通る（テストは erikak のパッケージ内に置く）。
- **SC-002**: 金型テストが、変更前に生成されたファイルを変えずに通る。差分は、番号の列のみ（テストで確認する）。
- **SC-003**: 他のホストプログラムのテストが、すべて通る（`go -C apps/server test ./...`）。
- **SC-004**: 保存データの読み込みで、記事番号の無い記事がエラーにならない（未決事項 1 の方針どおり）。

## スコープ外

- 記事の削除の操作（`K` など）の実装。
- 1 行入力と複数行入力（アペンドの本文の入力方式）の変更。`docs/research/ERIKA_K_APPEND_INPUT_EVIDENCE.md` の未確認事項。
- 他の板の番号の共通化、他のホストプログラムへの同じ採番の導入。
- 板の活動量、返信の計算（`planBoardActivity` の式）の変更。
- メインメニューや画面の文字列の変更。
- `.github/` の変更。

## 未決事項（人間の判断が要る）

1. **保存データの既存の記事**: 本仕様より前に保存された記事には、記事番号が無い。
   提案: 読み込み時に、板ごとに内部 ID の順で記事番号を補う（生成された記事は計画上の番号を優先）。
   補った番号は次の保存で書き出す。この変更で、既存の HAKATA の番号が一度だけ変わる。
   **この扱いで良いか、確認が必要。** 良くなければ、既存の記事は番号を持たず、一覧では内部 ID を出し続ける。
2. **生成された記事の番号と、人間の記事の番号の境界**: 計画上の `TotalRoots` と、既に保存された人間の記事の番号が衝突する場合の扱い。
   提案: 人間の記事の番号は `max(TotalRoots, 既存の記事番号の最大) + 1` から始める。
3. **返信の番号**: 返信（`ParentID != 0`）には記事番号を振らない（FR-005）。返信の内部 ID の扱いは、アペンドと同じとする。
   この前提で良いか確認する。
