# 返信・本文生成の実装状況と残作業

更新日: 2026-09-27

## この計画の対象

- 対象はMapleTownログ分析を受けた返信・本文生成の初期実装と、その後に必要な永続化・品質校正である。
- 変更対象は `apps/server/internal/llm/`、`apps/server/internal/worldengine/`、`apps/server/internal/worldrepo/`。
- ログから得た値はMapleTown局別の校正候補であり、歴史ソフト共通の仕様ではない。

## 作業ツリーにある実装

- `worldengine` に新規投稿・返信それぞれの本文長区間と、seedから区間を決める処理を追加した。重みはMapleTownの1996年ログ分析による局別校正候補で、歴史ソフト共通の仕様ではない。
- `worldrepo` からLLM rendererへ、投稿種別、親記事、引用文、本文長区間を渡す。
- Azure OpenAIの本文プロンプトへ上記制約を渡し、本文長に応じた出力トークン上限を使う。
- 選択済み引用は共通materializerでも検査する。引用がなければ原文を付け、異なる引用行があれば生成結果を拒否する。文字数検証では引用行を本文の新規記述から分ける。
- `min`は文章を水増しさせないためsoft target。最大本文長8,192文字、引用なし本文の上限、件名上限36文字は暫定的な生成ガードであり、各ホストプログラムの歴史的入力仕様を確定する値ではない。
- 既存の選択済み人物・canonical subjectをmaterializerが維持する既存契約を利用している。

## 残作業

### 1. 分析根拠を変更と一緒に追跡する

- MapleTownの分析文書・集計値を実装の根拠として参照可能にする。値には「局別ログからの校正候補」という注記を保つ。

### 2. 生成計画と本文の確定を永続化する

- 現在のband/引用選択は記事ID等から毎回再計算する。選択結果、seed、profile version、引用元記事と抜粋範囲を本文と一緒に保存し、コード・プロフィール更新後や再起動後も生成条件を再現できるようにする。
- 記事本文の生成状態を `planned / generating / ready / retryable_failed` 等で区別し、DB側の行ロックまたはCASとidempotency keyで同時生成を抑止する。
- 現在の `observationBodyJobs` はRepositoryインスタンス内の重複要求をまとめるもの。複数プロセス・再起動をまたぐleaseではない。`PostUpdater.UpdatePost` も期待versionを比較しないため、保存競合を防ぐ永続境界が必要。
- 保存が成功した結果だけを完成本文として返し、競合に負けた生成は既に保存された本文を読み直す。保存失敗を生成成功として扱わない。

### 3. ホスト固有の返信関係と引用選択を拡張する

- `prepareBoardComposition` は `RespondsToPostID`、`SourcePostID`、`ParentID` の順で同一board内の返信元記事を解決する。この優先順はテスト済み。
- 親本文未生成時は依存本文を先にmaterializeする。親記事が存在しない、閲覧・引用権限がない場合は引用を作らない。
- 今の引用選択は親本文の最初の非空行を最大160文字で使う。返信内容に関連した範囲選択、本文内の複数箇所引用、引用の前後に文章を挟む構造は後続課題とする。

### 4. 各providerの出力上限・完了検証を揃える

- Azure OpenAIには本文長に基づく`max_output_tokens`を送る。本文上限はpromptだけに依存せず、保存前validationでも検証する。
- 本文長帯・引用を含む総長・引用を除いた新規本文長の計測規則を固定し、CRLF/LF、全角・半角、引用行、署名を含む境界テストを追加する。
- 生成が途中で切れた、JSONが壊れた、本文が空、非引用部が空、上限を超えた場合の扱いを明確にする。修復する場合は同じ保存済みcomposition planで回数・deadlineを制限する。
- 文章長はsoft targetのため、実現長の分布・band別成功率・修復率・fallback/失敗率を計測する。上限検証だけで分布再現済みと判断しない。

### 5. ホスト表示と局別プロファイルを確認する

- 8,192文字までの本文が各ホストの本文表示・ページ送り・メモリ／転送上限と整合するか確認する。表示コマンドや折返しはホストランタイム所有とし、共通runtimeへ一律化しない。
- 返信・新規投稿の重みは局別／会話種別の候補としてversion管理し、別ホストへ無条件に適用しない。新規記事の長文裾は資料的記事が含まれる可能性を考慮する。
- 件名36文字も共通歴史仕様とは見なさず、各ホストが保持・表示できる上限とsemantic subjectの意味を確認する。

### 6. 分布と会話品質を校正する

- 100〜200件程度の隔離生成で、新規／返信、短文／長文、引用あり／なしを分けて確認する。これは希少な長文率やP99の精密推定には足りないため、裾ケースは個別fixtureでも確認する。
- band選択率と実現文字数、P50/P90、引用原文一致率、人物・subject維持率、provider別失敗率を比較する。
- 文字数を満たすための冗長化、引用だけで返信本文がないケース、毎回の質問締めや顔文字過多を品質確認に含める。

### 7. 自律的な返信選択は独立した後続機能とする

- 今回の実装は、既にworld layerが選んだ記事を言語化する処理である。記事を読む／無視する／返信する／独立投稿する判断自体は追加していない。
- 返信確率をログの`Re:`率で代用しない。人物の活動・閲覧履歴・関係・動機・無反応をworld layerが決めてからcomposition planを作る。
- `WorldClock`、親記事の投稿時刻からの返信遅延、観測済み履歴との整合、投稿のPostgreSQL永続化を含めて別PRで実装する。

## 次の完了単位

まず現在の未コミット差分をbranch/PRにし、上記1〜4のComposition永続化・CAS・provider上限・検証を整える。その後にホスト表示確認とログ校正を行う。自律返信選択はその完了後の別PRとする。
