# SDD-005: チャネル横断のインタラクション・フィードバック

Status: specified, not implemented
Updated: 2026-10-10

## 目的

掲示板の書き込み・返信（アペ）、メール、チャット、電報、SYSOP の処置など、世界の中で**動的に発生したすべてのインタラクション**を、
チャネルの違いを越えて相互に作用させ、各住民（人間の会員を含む）の**次の行動の選択**と、その行動を言語化するときの**文脈**に反映させる。

例:

- B が掲示板で A の質問に答えた → A は B に好感を持ちやすくなり、後日 A が「教えてもらったやり方で直った」と報告する根拠ができる。
- 人間の会員が C にメールで相談した → C はしばらくして（C の活動リズムに沿って）返事を書くか、書かない。返事を書いた場合、C は相談の内容を
  公開の板で勝手に話さない。
- チャットで D と E が新作ゲームの話をした → D が後日ゲームの板に立てるルート記事の原因（`interaction_followup`）になりうる。
- 板で F と G が口論した → 二人の関係に緊張が残り、次に同じスレッドで出会ったときの反応確率と語調に効く。SYSOP の注意が入れば、それも効く。

## 位置づけ（他の SDD・spec との関係）

```text
SDD-001 / 001.1  記事の canonical-before-prose
SDD-002          確定した投稿から人物の履歴を育てる
SDD-003          「言ったこと」と「本当のこと」を分ける（ClaimEvent）
SDD-004          住民が観測したことだけを思い出す（観測・関係の疎な検索）
spec 008         ペルソナ特性にもとづくレスの担い手・時刻の決定（LLM を使わない）
SDD-005（本書）  上記をチャネル横断に一般化し、「相互作用 → 派生状態 → 次の行動」の閉路を定める
```

SDD-002〜004 は掲示板の投稿（`post_id`）だけを前提にしている。spec 008 は「人間への私信（メール、チャット）への反応」と
「人物どうしの関係」をスコープ外にし、関係の項を常に 1 としている。本書は、それらを**置き換えずに**、共通の入力（インタラクション台帳）と
共通の派生状態を定義し、各 SDD/spec がそこから読むようにする。

## 現状の確認（2026-10-10 時点のコードと文書）

コードで確認した事実:

1. 人間の投稿は `world.Post{Author: <handle>}` として保存されるだけで、`AuthorPersonaID` も会員 ID も `Intent` も持たない
   （`hostprogram/erikak/runtime.go`、`hostprogram/turbobbs/runtime.go`、`bbs/runtime.go`）。誰が書いたかを関係・観測の主体として扱えない。
2. メールとチャットは Erika-K / TurboBBS ともに固定文言のスタブで、保存先がない（`erikak/runtime.go` のコメント
   「The shared world.Store currently has no IDS.BBS/private-mail persistence」）。
3. `world.Persona` には `Relationships`、`CurrentGoals`（進行中の会話・目標）に相当する項目がない。
   `PRODUCT_SPEC.md` と `WORLD_SIMULATION.md` は、これらを住民の持つ状態として列挙している。
4. 本文生成の文脈（`worldrepo/bbs_render_context.go`）は、同じスレッドの過去投稿と、同じ板の「関連投稿」を、
   書き手が読んだかどうかに関係なく渡している（プロンプト上では「読んだ証拠ではない」と注記している）。
5. SDD-002/003/004 と spec 008 は未実装（spec 008 は Draft）。
6. HAKATA 評価局は CONNECT のたびに記事（人間の投稿を含む）を消すため、通話をまたぐ影響は評価できない（一時的な評価モード）。

文書間の矛盾・不足は「既存文書の是正」の節にまとめる。

## 基本原則

- **台帳が真実、派生状態はキャッシュ。** 動的に発生したインタラクションは、すべて追記専用の `InteractionEvent` として保存する。
  関係・観測・未決事項・意見の版などの派生状態は、台帳から決定論的に再計算できる。派生状態だけを書き換えて事実を作らない。
- **影響は World が決める。** 何がどれだけ次の行動に効くかは、World の決定論的な規則（＋任意の上限つき助言）で決める。
  LLM は「影響を受けた結果として選ばれた行動」を言語化するだけで、影響の有無や大きさを決めない。
- **人間も NPC も同じ規則。** 人間の行為に特別な倍率を与えない。人間の投稿・メールが無視されることも正常。
  （`AGENTS.md`「The human participant is one member of the world, not its protagonist」）
- **知っている人だけが影響を受ける。** 影響は、その出来事を観測できた行為者にだけ及ぶ（SDD-004 の一般化）。私信の内容は当事者以外に届かない。
- **時間を逆行しない。** 時刻 T の行動は、T より前に起き、T までにその行為者が観測した出来事だけから影響を受ける。
  後から実体化した事実が、既に存在する過去の投稿を変えない（SDD-002 の時間モデル）。
- **閲覧順に依存しない。** 派生状態は、本文（遅延生成）ではなく、行動選択時に確定した canonical な意味情報（`PostIntent` など）と、
  人間が実際に書いた原文から作る。人間がどの記事を先に開いたかで、影響の結果が変わらない。
- **背景事実は引き金ではない。ただし、宛てられた相互作用は原因になりうる。** 「既存文書の是正」1 を参照。

## 既存文書の是正

本書の作成にあわせて、次の矛盾・不足を各文書で是正した。

1. **「人物の事実は行動の引き金ではない」と「相互作用が次の行動に効く」の衝突**
   （`LLM_POLICY.md`「Persona facts are not action triggers」、SDD-002 非目標「making accumulated history a reason to post」、
   `PERSONA_CONTINUITY_OVERVIEW.md` の共通不変条件）。
   是正: 背景事実・興味・蓄積した履歴は引き続き引き金にしない。一方、**その行為者に宛てられた、または行為者が関与した具体的な相互作用**
   （返信された、質問された、メールを受け取った、約束した、口論中）は、`WORLD_SIMULATION.md` が既に挙げる「Current salience/event」の
   「interaction」に当たり、World が未決事項（2.3）として保持し、行動の原因候補にできる。区別を各文書に明記した。
2. **意見の不変と影響の両立**（`PRODUCT_SPEC.md`「Opinions are persistent facts」、`LLM_POLICY.md` の Windows 95 の例）。
   是正: 意見は直接上書きしない点を維持し、変化は根拠イベントつきの `opinion_shift`（2.4）でのみ起きると定義した。
   既存文書の「a separate world event」が何であるかを本書が定める。
3. **住民の状態に列挙された「relationships」「current goals / ongoing conversations」の実体がない**
   （`PRODUCT_SPEC.md`、`WORLD_SIMULATION.md`「Actor model」、`ARCHITECTURE.md` の World 所有物「relationship/opinion values」）。
   是正: これらは `Persona` の静的項目ではなく、台帳からの派生状態（2.2、2.3）であると明記した。
4. **メールが観測の契機として挙がっているのに、メール・チャットの世界モデルがない**
   （`PRODUCT_SPEC.md`「reading mail」、spec 008 のスコープ外、SDD-003/004 が投稿のみを前提）。
   是正: 台帳・スコープ・観測規則をチャネル横断で定義し（1、2.1、3.3、3.4）、SDD-002/003/004 に一般化の注記を加えた。
   spec 008 は Draft のまま変更せず、本書の 3.1 で接続点を定めた。
5. **本文生成の「関連投稿」が書き手の観測と無関係に渡される**（`bbs_render_context.go`、`LAZY_PERSONA_FACTS.md` の注記）。
   SDD-003「Claims must never be injected merely because they exist globally in the database」と SDD-004 の観測フィルタに食い違う。
   是正: 重複話題の回避という用途に限る暫定措置であることを明記し、P3 で 3.6 の射影に置き換える。
6. **人間の投稿が主体として識別されない**（ハンドル文字列のみ）。是正: 1.1 で会員 ID を必須とし、`ARCHITECTURE.md` の
   「Current prototype shortcuts」に現状を記録した。

## 1. インタラクション台帳（共有の下位層）

### 1.1 InteractionEvent

チャネルに依存しない、追記専用の記録。論理的な項目:

```text
event_id              安定 ID（冪等キー）
world_key, host_id
channel               board_root | board_reply | mail | chat_utterance | chat_session | telegram |
                      sysop_action | presence（ログイン・ログアウトなど、必要になってから）
actor                 ActorRef（persona_id または member_id）
audience_scope        ScopeRef（下記）
addressed_to[]        ActorRef（メールの宛先、返信先記事の著者、電報の相手など。なければ空）
responds_to_event_id  直接の応答関係（返信、メールの返事、チャットの発言への応答）
content_ref           host-program 固有の実体への参照（post_id、mail_id、chat_line_id など）
occurred_at           世界時刻
semantic              World が確定した意味情報（NPC: PostIntent 由来。人間: 1.4 の注釈）
provenance            source_kind（npc_world_selected | human_authored | sysop | coarse_catch_up）
```

`ActorRef` は、NPC のペルソナと人間の会員を同じ型で指す。人間の会員は局ごとの会員 ID を持ち（局の会員登録と同じ単位）、
`world.Post` には `AuthorMemberID`（人間）または `AuthorPersonaID`（NPC）のどちらかを必ず入れる。ハンドル文字列だけを主体にしない。

### 1.2 ScopeRef（誰が見られるか）

```text
public_board(host_id, board_id)        その板を読める会員（局の閲覧権限に従う）
private(actor_set)                     メール・電報: 送り手と宛先だけ
chat_session(session_id)               そのチャットに居合わせた者だけ（途中参加は参加時刻以降のみ）
sysop_private(host_id)                 SYSOP（と運営側の会員）だけ
```

スコープは、観測・想起・開示の判定のすべてで使う。台帳を全文検索して文脈に入れることはしない。

### 1.3 host-program との境界

メールの一覧・既読・返信コマンド、チャットの入退室・電報の作法、掲示板のアペ表示などの**操作系は各ホストプログラムの実装**に残す
（`AGENTS.md`「操作系は別実装、世界データとインフラだけ共有」）。共有するのは:

- `InteractionEvent` の追記と、派生状態の読み出し;
- 私信・チャットの本文を保存する汎用の保存層（メール 1 通、チャット 1 行という単位。表示形式は持たない）;
- スコープによるアクセス判定の部品。

あるホストに歴史的にメールやチャットが無い場合、そのホストでは該当チャネルのイベントは発生しない。共通メールUIを作らない。

### 1.4 人間の発言の意味注釈

人間が書いた原文は、そのまま canonical な発言である。影響の計算に必要な最小限の意味情報（話題キー、宛先、質問か否か、
相手への賛否・感謝・依頼・約束などの「行為」）は、次の順で一度だけ注釈し、イベントに保存する（以後変えない）:

1. ホストの構造（返信先、メールの宛先）と字句規則（局・時代のデータで拡張できる語彙表。spec 008 FR-011 と共有）;
2. 取れない場合のみ、任意の構造化抽出（spec 008 FR-013 の話題タグ付けと同じ差し込み口。1 イベント 1 回）。

注釈は「人間がそう書いた」ことの表現であり、人間の内心を推定しない（SDD-003「Human boundary」）。
抽出が使えない・失敗した場合は、構造情報だけで処理を続ける（影響は弱くなるだけで、止まらない）。

### 1.5 観測されないチャネルは粗く扱う

NPC どうしのメールやチャットは、人間が観測できない。これらは**文章を生成しない**。必要な場合だけ、
粗いイベント（「C と D がメールでやりとりした」「関係が少し近づいた」「D が C から X の情報を得た」）として台帳に入れる。
本文は永久に未実体化でよい（`WORLD_SIMULATION.md`「Observation and lazy generation」）。

## 2. 派生状態

すべて台帳からの決定論的な畳み込みで、`event_id` 単位で冪等。疎に保ち、全ペア・全会員×全投稿の表を作らない（SDD-004）。

### 2.1 観測（SDD-004 の一般化）

強い観測として次を加える:

- メールの送り手・宛先（宛先は**読んだ時点**から。NPC が読む時点は 3.3 の活動リズムで決める）;
- チャットの参加者（参加していた時間帯の発言のみ）;
- 電報の送り手・相手;
- World が「読んだ」と選んだ行為者（spec 008 の返信の担い手は、返信先を読んだことになる）。

弱い観測（板の既読カーソル）は SDD-004 のとおり。

### 2.2 関係（RelationshipEdge）

意味のある相互作用があったペアにだけ作る。方向つき（A→B と B→A は別）:

```text
from_actor, to_actor, host_id（主な場）
interaction_counts_by_channel   board_reply / quote / mail / chat / telegram
last_interaction_at
affinity      [-1, 1]  好意
trust         [ 0, 1]  信頼（助言が役に立った、約束が守られた）
tension       [ 0, 1]  緊張（口論、無視、否定）
familiarity   [ 0, 1]  なじみ（接触回数と最近さから）
version, last_event_id
```

更新規則は、イベントの**行為の種類**（感謝・同意・反論・回答・依頼の無視・約束の履行など）と、受け手の性格
（`Argumentativeness`、`NewcomerOpenness` など）から決める**固定の小さな増減**とし、時間で中立に減衰させる。
係数は架空の調整値で、歴史統計ではない（spec 008 と同じ扱い）。

注意: 減衰は**読み出し時に計算**し、保存値を時刻ごとに書き換えない。

### 2.3 未決事項（OpenLoop / Agenda）

「次の行動の原因」になりうる、行為者ごとの開いた項目。これが、相互作用を次の行動に結ぶ主な経路である。

```text
loop_id, owner_actor, kind, source_event_id, counterpart_actor, scope,
topic_keys[], created_at, due_hint, expires_at, status(open|resolved|expired|abandoned), resolved_by_event_id
```

`kind` の例（開いた集合。コードの閉じた列挙にしない。下は初期の生成規則の対象）:

- `addressed_question` 自分宛ての質問・相談（板の返信、メール）;
- `unanswered_mail` 受け取ったメール;
- `own_question_answered` 自分の質問に回答がついた（報告・礼の原因）;
- `commitment` 自分がした約束（「試してみます」「今度持っていきます」）;
- `dispute` 続いている口論;
- `chat_topic_carryover` チャットで出て、まだ板では話していない話題;
- `sysop_notice` SDD 外の処置（注意・削除）を受けた。

規則:

- 未決事項は**宛てられた／自分が関与した具体的な相互作用**からだけ生まれる。背景事実・興味・過去の話題の存在だけからは生まれない。
- 期限・減衰があり、多くは何もされずに `expired` になる（無反応は正常）。
- 解決は台帳のイベントで行う（返事を書いた、報告した、謝った、口論から抜けた）。
- 1 行為者あたりの同時に開いている項目数に上限を設ける。

### 2.4 意見の版（OpinionVersion）

`Persona.Opinions` を直接上書きしない。変化は `opinion_shift` イベント（version つき）としてのみ起きる。

- 発生は World が決める: 信頼の高い相手からの説得、自分の体験（canonical な出来事）、多数の観測など、根拠イベントを必須とする。
- 1 回の変化幅に上限を設け、性格（頑固さ・議論好き）で確率と幅を変える。
- 人間の発言も NPC の発言も同じ規則。LLM が相手に同調した文章を書いたことは、意見変化の根拠にならない。

これにより `PRODUCT_SPEC.md` の「Opinions are persistent facts」と「影響を受けて変わりうる」を両立させる。

### 2.5 話題の顕著さ（TopicSalience）

板・局・行為者の単位で、最近の相互作用に現れた話題キーの顕著さを、日付範囲・減衰つきで持つ（spec 008 FR-011 の「顕著さ」を、
世界イベントだけでなく相互作用から上げる）。顕著さは**確率の補正**であり、それ単独では投稿の原因にならない。

### 2.6 人物の履歴・発言（SDD-002 / 003 の入力の一般化）

- SDD-002 の履歴候補、SDD-003 の `ClaimEvent` の出典を `post_id` から `event_id` に一般化し、`scope` を持たせる。
- 私信・チャットで開示された事実は、その `scope` の参加者だけが知っている。公開の板で別の行為者がそれに言及するには、
  World が開示（うわさ・本人の再言及）を選ぶ必要がある（3.5）。

## 3. 次の行動への反映

### 3.1 掲示板の返信（spec 008 への接続）

spec 008 の担い手の重みに、次の項を掛ける（どれも上限・下限つき、既定値 1）:

- `relationship(A→著者)`: familiarity・affinity・tension の関数。緊張が高いと、議論好きは返信しやすく、そうでない人は避けやすい;
- `open_loop(A)`: その記事が A の未決事項（自分宛ての質問、続いている口論）を解決できるなら上げる;
- `observation`: A がその記事を観測できる（板の閲覧権限・活動）こと。担い手に選ばれたことが、そのまま観測の記録になる。

spec 008 の「関係の項は常に 1」は、本書の実装時にこの項へ置き換える（差し込み口は spec 008 が既に用意している）。

### 3.2 ルート記事（Situation-first 計画への接続）

ルート記事の原因候補に、行為者の未決事項を加える:

```text
cause_kind = interaction_followup
source_event_id = 未決事項の source_event_id
```

- World が、通常の open-topic の原因と未決事項由来の原因を、行為者の性格・未決事項の古さ・顕著さから重みつきで選ぶ。
- Situation モデルには、選ばれた原因と、行為者が観測できる範囲の元イベントの要約（3.6）だけを渡す。
- `LLM_POLICY.md` の「A continuation is especially strict」を満たすため、`interaction_followup` は**新しい進展**
  （試した結果、得た情報、気持ちの変化など、World が確定したもの）を必須とし、前の投稿の言い換えを許さない。

### 3.3 メール

- NPC がメールを**読む**のは、その NPC の次の擬似ログイン時刻（spec 008 FR-012 の活動リズム）であり、到着と同時ではない。
- 読んだ後に返事を書くか（`unanswered_mail` の解決）、書かずに失効させるかを、関係・性格・内容の行為（依頼・質問・礼）から決める。
  書く場合の予定時刻は spec 008 の遅延分布と同じ考え方で決め、保存する。
- 自発的なメール（板の口論を私信に移す、助けてもらった礼、オフ会の誘い）は、関係と未決事項がある場合にだけ、低い確率で選ぶ。
- 実体化は観測駆動: 人間が自分のメールボックスを開いたときに、その人宛ての予定済みメールのうち予定時刻を過ぎたものだけを実体化し、
  本文を生成する。NPC どうしのメールは 1.5 のとおり粗いイベントのみ。

### 3.4 チャット・電報

チャットは同期的なので、他のチャネルと決め方が異なる:

- NPC がチャットに居るか、呼び出し（CALL・電報）に応じるかは、回線の占有と活動リズム（`WORLD_SIMULATION.md`「Lines and presence」）で決める。
  居ない人は応じない。
- 1 発言ごとに、World が「応答する／短く返す／黙る／退室する」を決定論的に選び、応答する場合だけ LLM が言語化する。
  発言間隔はホストの出力ペース（bps）と人物の性格で決める。
- 発言は `chat_utterance` として逐次保存する（会話の真実は LLM のセッションではなく台帳）。
- セッション終了時に、決定論的規則（＋任意の構造化抽出、1 セッション 1 回）で、関係の更新・未決事項（`chat_topic_carryover`、`commitment`）・
  履歴候補を作る。

### 3.5 チャネル間の情報の流れと開示

- 私信・チャットの情報が公開の板に出るのは、World が開示行動を選んだときだけ:
  本人の再言及（自分の事なら自由度が高い）、他人の私信の暴露（性格・関係・局の規範で非常に低い確率。起きればそれ自体が事件で、
  `tension` と SYSOP の処置の対象になりうる）。
- 公開の板で見たことは、メール・チャットで自由に参照してよい（観測していれば）。
- 局をまたぐ伝播（うわさ、共通会員）は、`WORLD_SIMULATION.md`「Local communities」の辺に沿ってだけ起きる。全世界の検索にしない。

### 3.6 言語化の文脈（ActorKnowledgeProjection）

行動が選ばれた後、本文・件名・チャット発言の生成に渡す文脈は、次の手順で作る小さな射影（およそ 3〜8 項目）に限る:

```text
選ばれた行動（actor, channel, target, cause, time）
 -> 候補: 直接の相手との関係の要約、解決しようとしている未決事項、
          同じ話題キーの過去の発言（自分・相手）、スレッド／会話の直前の流れ
 -> フィルタ: occurred_at < 行動時刻、かつ actor が観測済み、かつ scope が出力先と両立
             （公開の板への投稿に private の内容を入れない。開示が選ばれた場合だけ例外）
 -> 関連度・最近さで上位 N 件
 -> プロンプトの材料（指示ではなく、事実としての材料）
```

`ARCHITECTURE.md`「Context assembly」の 5（relationship summary）と 6（relevant recent messages/events）は、この射影で満たす。
関係の数値はそのまま LLM に渡さず、「何度かやりとりがあり、前回は助言をもらった」程度の事実の要約にする。

### 3.7 エージェンティックな過去発言・観測ログの参照（Actor-Scoped Tools）

3.6 の静的な文脈注入（プロンプトにあらかじめ上位数件を入れる方式）に加え、特にチャットや複雑な返信において、
**LLM が必要に応じてツールを呼び出し、過去の発言や観測ログをオンデマンドで調べるエージェンティックな仕組み**を設ける。

#### ツールの役割と境界（AGENTS.md との調和）

- **World が行動を決め、エージェントが記憶を引く**:
  チャットで応答するか、無視するか、退室するかといった「行動の決定」は World が行う（AGENTS.md 原則）。
  「応答する」と決まったあとの言語化フェーズにおいて、エージェント（LLM）が会話相手の質問内容に応じてツールを呼び出す。
- **話者の観測可能範囲（Scope）に厳格に閉じる**:
  ツールが返す検索結果は、その話者（`actor`）が**実際に観測できたイベントのみ**にフィルタされる（SDD-004 / SDD-005 §2.1）。
  他人の私信、未読の板、参加していないチャットセッションの内容は、ツールをどう検索しても絶対に返らない。
- **世界事実の書き換え禁止**:
  ツールはすべて**読み取り専用（Read-Only）**。エージェントがツールを通じて世界の事実や関係の数値を直接書き換えることはない。
  新しい事実は、エージェントが発言したあと、World が台帳に `chat_utterance` 等として記録することで生まれる。

#### 提供するエージェントツール（読み取り専用・Go実装: `internal/llm.StandardActorTools`）

```text
1. get_my_recent_posts(board_id?, limit=3)
   自分が直近に書いた掲示板の投稿（記事番号・板・件名・本文抜粋・日時）を取得する。
   用途: チャット等で相手から「さっきBBSに書いてた件」と聞かれたときに、自分が何を書いたか確認する。

2. get_thread_context(thread_root_id, limit=3)
   特定のスレッドにおけるこれまでの投稿の流れ（親記事および直前のレス）を取得する。
   用途: スレッドの文脈を再確認し、重複しない意見や自然な返信を書く。

3. get_interaction_history_with(counterpart_id, channel_filter?, limit=3)
   特定の相手（人間の会員や他のNPC）との直近のやり取り（チャット発言、メール、掲示板での返信）を取得する。
   用途: 「昨日チャットで話した続き」や「以前メールで相談された件」を踏まえて会話を継続する。

4. search_my_observed_events(query, channel_filter?, limit=3)
   自分が観測した掲示板記事、参加したチャット発言、受信したメールから、キーワードや話題で検索する。
   用途: 「前に言ってたあのゲームの話」「あのスレで出てた解決策」を思い出す。

5. get_my_open_loops(limit=3)
   自分が現在抱えている未決事項（自分宛ての質問、未返信のメール、約束、継続中の議論など）の一覧を取得する。
   用途: 宿題や約束、気になっていた話題を確認し、フォローアップ記事を書くときの拠り所にする。

6. get_my_profile_facts(topic?)
   自分の確定した人物事実（PersonaFact：所有機種、OS、居住地域、趣味など）を取得する。
   用途: 自分の過去の環境発言と矛盾しないように確認する。
```

#### 反応性とレイテンシの制御（各作成要求に対し最大1回の往復）

対話のテンポとサーバーリソースを維持するため、各文章生成（1回のBBS本文生成、1ターンのチャット発言生成）におけるツール呼び出しは**差し当たり最大1回（1 round-trip）**に制限する（`DefaultToolExecutionPolicy.MaxToolCallsPerTurn = 1`）。

```text
Round 1 (初回生成要求):
  - システムプロンプト + コンテキスト + 上記ツール定義一覧（ToolDefinitions）を提示。
  - LLM の判定:
    - Case A: ツールを呼ばずに直接テキストを出力 → そのまま完了（計1回のLLM呼び出しで最速終了）。
    - Case B: ツール呼び出し（ToolCall）を要求 → バックエンドがローカルDBから即座に結果（ToolResult）を取得。

Round 2 (最終出力生成):
  - ツール結果（ToolResult）を会話履歴に含め、再度LLMを呼び出す。
  - この2回目の呼び出しではツール定義を外す（tool_choice="none"）ことで、必ず最終発言・本文を出力させて完了。
```

- **効果**:
  - LLM の呼び出し回数は **最大2回**（ツール不使用時は1回）に確実に抑えられ、予測可能なレイテンシ（数秒以内）を保証する。
  - ツール実行自体はインメモリまたは高速インデックス検索（ローカルDB）のため、ミリ秒単位で完了する。

#### ツールの内部実装アーキテクチャ（生成LLMを使わない超高速化）

ツールの実行処理（Tool Execution）自体には**生成LLMを一切使わず**、インメモリ直接参照およびEmbeddingベクトル検索（`text-embedding-3-small`）を採用する。これによりツール実行処理時間を 0.1ms〜20ms 未満に抑え、ツールの内部処理による遅延を実質ゼロ化する。

```text
1. インメモリ直接参照（実行時間: < 0.1ms）:
   - 対象: get_my_recent_posts, get_thread_context, get_interaction_history_with,
           get_my_open_loops, get_my_profile_facts
   - アクターが観測した直近データは局あたり高々数十〜数百件のため、メモリ上のマップ/スライスから
     直接O(1)で切り出して返す。

2. Embedding ベクトル検索（実行時間: 5〜20ms）:
   - 対象: search_my_observed_events(query)
   - 生成タイミング（非同期マイクロバッチ原則）:
     - 記事保存やチャット発言のたびに直列で API を呼ぶとレイテンシ悪化や障害巻き込みのリスクがあるため、
       保存処理自体は即座に応答を返し、直後に非同期キュー（Go channel）へ投入する。
     - バックグラウンドの軽量ワーカが「10件溜まる」または「200ms経過」でマイクロバッチ化し、
       デプロイ済みの「text-embedding-3-small」へ一括送信してベクトルを保存する。
     - なお、BBSの初期ヘッダ計画（Situation-First）のように元から最大10件が配列で存在する処理は、
       ヘッダ確定時に1リクエストのバッチでまとめて埋め込む。
   - ツール呼び出し時:
     - 検索クエリをEmbedding化（約10ms）し、観測済みベクトルの内積計算（コサイン類似度）を一瞬（<1ms）で実行。
     - 観測境界（Scope Filter）でフィルタし、本人が観測可能な上位を抽出して返す。
     - 生成LLMと違ってトークンを逐次生成しないため、超高速かつ表記揺れに強い話題想起を実現する。
```




#### 代表的なシナリオの流れ

1. **シナリオ A: チャットでの会話 → 翌日の BBS への波及（Chat to BBS Carryover）**
   - チャットで人間会員と A さんが新作ゲームについて盛り上がる。
   - セッション終了時、A さんに未決事項（`OpenLoop`: `kind=chat_topic_carryover`, topic="ゲーム名", counterpart=USER）が記録される。
   - 翌日の世界時刻において、WorldEngine の行動選択で A さんのルート記事起票が選ばれ、未決事項から `cause_kind=interaction_followup` が採択される。
   - A さんの記事生成時、エージェントは `get_interaction_history_with(USER)` または `chat_topic_carryover` のコンテキストを参照し、
     「昨日チャットである方と話していたのですが、気になってスレを立ててみました」といった自然な波及記事を書き込む。

2. **シナリオ B: BBS の書き込み → チャットでの質問と参照（BBS to Chat Reference）**
   - B さんが BBS の「PC-98 技術板」に特定グラフィックボードの設定に関する記事を投稿する。
   - その後、人間会員がチャットで B さんに「B さん、さっき掲示板に書いてたグラボの設定だけど、ディップスイッチはどうしたの？」と質問する。
   - B さんの応答言語化時、エージェントは相手の発言から「自分が掲示板に書いた内容が問われている」と判断し、
     `get_my_recent_posts()` ツールを実行して直近の自投稿を取得する。
   - 取得した記事内容に基づき、「ああ、さっき技術板に書いた GA-98NB の件ですね！あれは SW2 の 3 番を ON にして…」と的確に応答する。


## 4. 決定性・冪等性・同時実行

- 派生状態の更新は `event_id` で冪等。同じイベントを 2 回畳み込んでも結果は同じ。
- 派生状態は「台帳のどこまでを反映したか（`last_event_id`／version）」を持ち、計画時はその version を読み、
  コミット時に比較する（`LLM_POLICY.md`「Concurrency and idempotence」）。
- 予定済みの行動（返信・メールの予定）は、計画時の状態で確定し保存する。後から入ったイベントで計画を書き換えない。
  ただし本文の言語化は、その行動の予定時刻より前に観測可能だったイベントを文脈に含めてよい（時刻フィルタは 3.6）。
- 遅延した観測で古い期間を追いつかせる場合、イベントを世界時刻順に畳み込む。粗い追いつき（`coarse_catch_up`）のイベントも同じ台帳に入れる。

## 5. 人間を主人公にしないための検査

- 同じ特徴（板、時刻、話題、宛先の有無、関係）を持つ人間の投稿と NPC の投稿で、返信が付く確率・遅延の分布に、
  統計的に有意な差がないことをテストする。
- 人間のメールに対する NPC の返信率は、NPC どうしの（粗い）メール返信率と同じ規則から出る。
- 人間に関係する派生状態の更新回数に、人間専用の上限・下限を設けない。

## 6. 実装の段階と Spec の分離
 
 本設計書（SDD-005）は全体の青写真・アーキテクチャ境界を定義するものであり、実装は肥大化を防ぐため、
 本リポジトリの運用ルール（`AGENTS.md` / `specs/README.md`）に従って**独立した Spec（`specs/NNN-name/`）に切り出して段階的に実装**する。

### 実装フェーズと推奨 Spec 構成

1. **`specs/010-interaction-ledger`（基盤台帳・関係エッジ）**:
   - P1: 会員 ID の保持、`ActorRef`、`InteractionEvent` の追記。
   - P2: 観測境界と `RelationshipEdge` の決定論的計算。
2. **`specs/011-actor-memory-tools`（記憶想起ツール・非同期埋め込み）**:
   - P3 相当: 6 つのエージェントツール（`StandardActorTools`）のバックエンド実装。
   - 非同期マイクロバッチ埋め込みワーカ（`text-embedding-3-small`）とコサイン類似度検索の実装。
   - 各作成要求に対する最大 1 往復（`MaxToolCallsPerTurn = 1`）のオーケストレーション。
3. **後続 Spec（P4〜P7）**:
   - メールの保存層と自律返信、チャットセッション、局間伝播。

| 段階 | 内容 | 主な変更先 |
|---|---|---|
| P1 | 主体の識別: 人間の投稿に会員 ID、`ActorRef` の導入。`InteractionEvent` の追記（板のルート・返信のみ、NPC と人間）。 | `world`、`worldpersist`、各 host-program の投稿保存箇所 |
| P2 | 観測・関係の派生（SDD-004 の中核）。spec 008 の関係の項を実装。 | `world`／新しい共有パッケージ（例 `interaction`）、`bbsengine` |
| P3 | 未決事項（板由来の `addressed_question`、`own_question_answered`、`dispute`）。返信重みとルート原因 `interaction_followup` への接続。3.6 の射影で `bbs_render_context` の「関連投稿」を置き換える。記憶参照ツール・非同期埋め込みの統合。 | `bbsengine`、`worldrepo`、`llm` |
| P4 | メールの保存層と、ホストごとのメール操作（歴史資料のあるホストから）。NPC の受信・返事の計画、観測駆動の実体化。 | 共有保存層、`hostprogram/<host>/` |
| P5 | チャット・電報: 在席判定、発言ごとの行動選択、セッション終了時の派生。 | `telephone`（回線占有）、共有保存層、`hostprogram/<host>/` |
| P6 | SDD-002/003 のチャネル横断化（`event_id`・`scope`）、意見の版（`opinion_shift`）、開示の規則。 | `world`、`worldengine` |
| P7 | 局をまたぐ伝播（うわさ・共通会員）。 | `worldengine` |

### 評価運用とリセット方針の整合

現在の HAKATA 評価局における「CONNECT ごとの記事リセット」は、評価・開発の再現性を保つため**そのまま維持**する。
その上で、本仕様の伝播シナリオ（チャット翌日の BBS 書き込みや、BBS 投稿のチャット参照）を検証・評価する手段は次のとおりとする:

1. **同一通話内のチャネル横断（即時性のある波及・参照）**:
   - シナリオ B（BBS で読んだ内容を、その後のチャットで質問・参照する）は、同一通話内の遷移（BBS 閲覧 → チャット入室）でそのまま動作・評価可能。
2. **通話内での疑似時間経過 / 日送り（In-Call Time Advance）**:
   - シナリオ A（チャットの「翌日」に BBS に書き込まれる）を通話中に体験・評価するため、デバッグ/管理コマンドまたは時間経過シミュレーション（例: テレホ時間経過や疑似日送り）により、同一通話内で世界時刻を進めて翌日分の BBS キャッチアップを走らせる仕組みを評価支援として利用できる。
3. **決定論的シナリオテスト（Golden / Fixture Tests）**:
   - 台帳イベントの追記から派生状態の計算、翌日のルート記事計画、チャット応答ツールの呼び出しに至る一連の閉路は、通話セッションとは独立した純粋なバックエンドのシナリオテスト（`go test`）で完全に決定論的に検証・回帰防止を行う。


## 非目標

- すべての文を ClaimEvent にすること、全履歴の自然言語推論を毎回行うこと（SDD-003 と同じ）;
- 人間の内心・感情の推定;
- 観測されない NPC どうしの私信・チャットの本文生成;
- 共通のメール／チャット UI;
- 関係の数値をそのまま画面やプロンプトに出すこと;
- 反応率・応答時間の歴史的に正確な主張（数値は架空の調整値）。

## 受け入れ基準

- 板・メール・チャットのどのチャネルの出来事も、同じ台帳に `event_id` で一度だけ記録され、再試行で重複しない。
- 返信の担い手・メールの返事・ルート記事の原因の選択が、関係と未決事項によって期待どおりの向きに変わる（固定シードの統計テスト）。
- 観測していない出来事・スコープ外の私信が、行為者の文脈にも行動選択にも入らない。
- 公開の板の投稿の文脈に、開示が選ばれていない private の内容が含まれない。
- 意見は `opinion_shift` イベントなしに変わらず、LLM の同調的な文章は意見を変えない。
- 予定済みの行動と、実体化済みの投稿・メールは、後のイベントで書き換わらない。
- 人間と NPC で同じ特徴の行為への反応分布に有意差がない（5 章）。
- AI プロバイダなし（偽プロバイダ 0 回）でも、P1〜P3 の決定がすべて動く。
